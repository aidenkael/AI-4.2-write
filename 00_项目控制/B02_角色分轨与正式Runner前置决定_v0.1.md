# B02｜角色分轨与正式 Runner 前置决定 v0.1

> 日期：2026-08-09
> 状态：Controller 决定；用于正式 Runner 冻结前纠正候选角色错位。

## 一、关键发现

B02 上游冻结后发现：三个候选虽然都覆盖“人物心理 / 情绪传递 / 人物反应”，但它们的原生工作角色并不相同。

- `oh-story-claudecode`：明确包含中文正文生成侧方法，可直接作为生成赛道候选。
- `creative-writing-skills`：同时包含 Writer / Character Sim / Reader Sim / Critic / Editor 等角色，可拆成生成与诊断两类候选。
- `Apodictic`：核心定位是 development editor / diagnostic system；其 README 明确强调 Firewall：诊断、指出结构问题和解决方案类别，但不替作者改写正文。

因此不能简单把三者都强行改造成“同一种生成 Prompt”后宣称比较的是原项目能力。这样会把 Apodictic 的诊断能力误测成生成能力，也会把适配器质量混入上游能力差异。

## 二、B02 改为两条赛道

### B02-G｜情绪生成

目标：在同一个中性创作任务下，比较额外生成机制是否能稳定提升情绪传递。

首轮候选：

1. `D0`：strong baseline，同模型、无额外小说 Skill；
2. `G1`：oh-story 的最小情绪/正文生成机制子集；
3. `G2`：creative-writing-skills 的最小 Writer / Character Sim 生成机制子集。

Apodictic 不以“原项目”身份进入 B02-G。

后续 AI-write Candidate 暂不设计。只有在上游独立冻结并完成至少一轮可解释对照后，才允许吸收有效机制形成组合候选。

### B02-R｜情绪诊断与修订增益

目标：比较“诊断”能否帮助后续中性修订器把已有草稿改得更自然、更人物化，而不是比较谁直接写正文。

建议候选：

1. `R0`：无专项诊断 / 通用诊断 baseline；
2. `R1`：Apodictic Emotional Craft / Character Architecture 等最小诊断子集；
3. `R2`：creative-writing-skills Critic / Editor 相关最小诊断子集。

统一使用同一批预先冻结的有缺陷草稿；诊断输出与修订过程分离。若进入正式执行，应让同一个中性修订器只读取对应诊断结果，从而尽量隔离“诊断质量”与“改写模型能力”。

B02-R 暂不与 B02-G 同时启动。先完成 B02-G，再根据结果决定是否值得启动 R 赛道。

## 三、B02-G 的任务要求

保留三个异质情绪任务方向：

1. 爱情关系中的吃醋但不承认；
2. 权力差下受到羞辱但不能发作；
3. 重大丧失后的异常冷静 / 延迟反应。

正式基础题必须保持中性，不在任务正文里泄露待测机制，例如不得直接要求：

- “写出感知→解释→判断→冲动链”；
- “通过常态偏移表现情绪”；
- “必须安排误解、回避、身体微张力”；
- “禁止用某种具体机制而要求另一种机制”。

只约束故事事实、人物关系、场合、必须发生的事件、字数和明显禁用的情绪标签。机制只进入 Treatment runner。

## 四、减法约束

B02-G 所有 Treatment 适配必须遵守：

- 不把完整上游 Skill 全量塞入上下文；
- 只取与当前能力直接相关的最小机制子集；
- 删除工具路由、安装说明、无关工作流和与本题无关的检查项；
- 不要求逐项显式输出分析链；
- 不把情绪机制写成固定模板或动作字典；
- 不因规则更多、字数更长、token 更多而获得评价优势；
- 记录每个 runner 实际额外注入的文本长度 / token 成本。

## 五、作者评审

作者只看匿名小说结果，不看项目名、runner 名、token、文件数或许可证。

每个任务优先只问：

1. 哪个版本更愿意继续读 / 写；
2. 哪个版本更自然；
3. 哪个人物更像“这个具体的人”，而不是通用情绪演员；
4. 最想保留的一个具体设计；
5. 若有副作用，指出最明显的一处（过密、解释过多、套路动作、AI 炫技等）。

不要求作者判断内部术语。

## 六、正式 Runner 前必须完成

在启动 B02-G 前先完成：

1. 将 `B02_上游冻结与适配事实表_v0.1.md` 清理为可提交版本：只保留自有总结、文件路径、版本与必要短引，不复制大段上游 Prompt / 文档；
2. 为 D0 / G1 / G2 各写一份“实际注入机制清单”；
3. 给三个任务写完全中性的 base prompt；
4. 审查 base prompt 是否泄露目标机制；
5. 固定模型、reasoning、runner 隔离、输出长度、重试规则、匿名映射与成本记录方式；
6. 先提交协议与 runner 输入，不运行；由 Controller 最后检查后再开跑。

## 七、当前禁止

- 不直接把 Apodictic 改造成生成 Prompt 参加 B02-G；
- 不设计 AI-write 组合 Candidate；
- 不同时启动 B02-G 与 B02-R；
- 不把三个上游直接融合；
- 不把未验证机制写入 `04_写作知识库` 或生产 Skill；
- 不因为三家都提到反标签 / 反模板动作，就把这些共同规则当作新增能力；必须保留 strong baseline 验证增量。
