### 作者优先素材工作流（AUTHOR_FIRST_MATERIALS_WORKFLOW）

作者侧素材工作流只有：**导入 → 提纯 → 蒸馏 → 可用于写作**。原著与技巧书共用「提纯」「蒸馏」两个作者动作；UI 不让作者选择 SourcePrepare、MethodPrepare、BookDistill 或 MethodDistill，后端按 canonical 类型自动分派既有 Skill。

导入/识别阶段零 AI：不创建 classify request/pending 状态，不调用 Agent 分类，不轮询分类结果。新导入批次的作者入口已收敛为一次操作：作者选当前批次类型（原著/技巧类/其他）后，原著/技巧类点一次「提纯」、其他点一次「保存素材」；「提纯」内部机械完成 build intake plan → MaterialIntake apply → 对本次 new_ids 逐个调用现有 Prepare（plan/apply 是后台内部实现，不再是作者步骤，没有“生成入库计划/确认入库”两步，也没有逐本类型选择或逐本 REVIEW 编辑）。机械入库计划仍保持 exact_duplicate → ATTACH_EXISTING、unsupported → REVIEW、其余 → NEW_ASSET；plan 中存在 REVIEW 时不 apply，提示作者移出无法处理的文件后重试。格式白名单：EPUB/PDF/TXT（已移除 ZIP/MOBI/AZW3）。

一级导航固定为新增素材、已提纯素材库、写作素材库、素材总览；同一素材只出现在一个阶段。后端 workflow_stage 为 new/purified/writing/other 四值：other（LOOSE_MATERIAL/RESEARCH）不进入三生产区，只在素材总览的类型统计中出现，不伪装成待提纯。写作素材库提供全部、原著、技巧类、其他的简单筛选。

作者状态只使用待提纯、待蒸馏、正在提纯、正在蒸馏、需要检查、可用于写作。不得显示 PASS、REVIEW、FAIL、BKP、acceptance、retrieval-ready、fingerprint 或内部 Skill 名称。蒸馏是一个作者动作；原著内部的 BKP 定稿、全书综合验收、acceptance gate 与 KnowledgeRetrieve 可发现性检查，都是该动作的后台完成条件，不增加验收、加入知识库或定稿按钮。只有 KnowledgeRetrieve 已确认来源真实可发现/可加载，才能显示可用于写作。

作者详情只回答这本资料主要可学什么、适合解决哪些写作问题、当前能否用于写作。原著优先只读既有 `bkp/author_view.md`，技巧书只读既有 `method/method_profile.md` 与可直接复用的已解析方法卡；不得为 UI 建第二知识权威或额外调用模型。EPUB/TXT/PDF 共用同一作者工作流：保持 EPUB-first、TXT 既有质量门与只处理文字层 PDF；不新增 OCR、MOBI/AZW3/ZIP 转换器。格式不保证同等质量，Prepare 判定结构或正文质量有风险时，作者看到需要检查而不进入蒸馏。

长书/短书不是作者概念：不加类型、标签、设置或按钮；不建设章节级实时进度协议，只显示正在蒸馏。未完结或连载来源不因未完结本身被拒绝，验收只覆盖当前冻结来源与当前可支持的发现；结论必须限制在当前范围，不得伪称终局结构、完整人物弧或最终主题。来源更新仍由既有 SHA/fingerprint 机制识别。

本阶段不得新增第二素材 registry、第二 Agent runtime、第二知识库、向量/RAG/KG、通用进度事件系统或格式专用蒸馏框架。

### 作者优先、稀疏地基合同（AUTHOR_FIRST_SPARSE_FOUNDATION）

作品地基是 Go Write 可持续维护长期故事事实的能力模型，不是作者必须完成的检查表。ProjectModel 中存在某个字段，只表示存储、AI 与下游 Context 可以在作品真正需要时承接它，不表示作者界面必须展示或要求填写。地基从作者决定、已接受规划和已接受正文中逐步生长；不得设置大型必填人物、世界或 system 模板，也不得以缺少可选地基字段阻断规划、写作或检查，除非既有硬合同确实要求该字段。

作者界面默认稀疏：新建和编辑只展开最小有用核心字段；高级字段默认收起，并以紧凑数量提示已有内容。作者可显式展开「更多信息」查看和编辑已有高级值及自定义字段；空高级字段不得形成空白 textarea 墙。收起保存必须保留未编辑的已有值，空字段不自动补齐，遗留/自定义数据不得因本次未显示而丢失。

输入只分四类，不建设通用属性框架：

1. 创造性语义继续使用 text / textarea；
2. 只有当前后端或手册已有规范、有限选项时，才使用 select / radio；
3. 指向现有项目对象的引用，在中央关系类型已存在时复用 RelationSelector、稳定 ref 与显式 dependency；
4. 随 AI/正文演进的动态状态继续由既有 authority / change settlement 维护，作者可以覆盖，但不得成为建书前置问卷。

明确禁止 Generic Schema Builder、Notion 式属性引擎、通用 ontology、新图数据库、第二关系引擎、新 Foundation 状态库、题材专用领域 Skill，以及魔法/修炼/职业/经济专用数据模型。成熟写作/PKM 产品只借鉴简单笔记、选择性元数据、typed references 与隐藏空属性等产品经验；不得复制 GPL/AGPL 代码。Go Write 继续以 ProjectModel、active_modules、field_config、显式 dependencies 与 RelationSelector 为基础。

`system` 保持唯一通用成长/规则域，`character_uses_system` 保持人物到体系的 canonical 关系。只有人物恰好选择一个 system 且该记录已有可安全解析的 `levels_stages` 时，CharacterEditor 才可用这些真实值显示 `current_level` 下拉；无可用层级、零个体系或多个体系含义不明时不得推测层级，只保留可选高级文本能力。已有但不匹配的 `current_level` 必须安全可见并保留。本阶段不新增 `stage_id`、阶段实体或子对象体系；更强身份只在真实连续使用证明必要后再评估。

地基随作品生长：Author Intent、FoundationDesign 与 planning 只提出当前作品确实需要的记录；作者确认/编辑后继续走既有 authority writeback。已接受正文、章节实际结果与作者显式「更新作品状态」可通过既有 settlement 演进受影响动态状态；Foundation 展示最新 authority，StoryPlan、StoryWrite 与 Review 通过同一 Context 读取它。不得常驻全书 AI 维护，也不得增加强制 wizard。

本阶段正确使用全部已有中央显式关系类型，不因某个文本字段在概念上可引用对象就新增关系类型。没有当前 canonical relation 的字段保持可选高级文本；只有既有权威语义无法闭环时，才允许以真实 consumer 证据提出新关系，默认 `DO_NOT_BUILD`。

Story Map 仍是同一 ProjectData/authority 的派生视图。关系图可直接新增/编辑人物和关系，但必须挂载共享 CharacterEditor / RelationshipEditor 并走同一 author_edit/writeback；不得拥有 graph-local 业务状态。`loading` 只表示首次或无数据加载；保存后的同项目刷新保留已加载图，不得闪空或卸载。人物节点固定为头像 → 姓名 → `one_line_intro` 居中堆叠，优先使用 Cytoscape 原生换行/包裹能力，不为此增加 plugin 或 DOM overlay。

本次是一个完整产品闭环阶段。检查点提交只作回滚点，不构成中间作者验收；只有全部实现和自动验证完成后，状态才可写为 `已实现并自动验证，待作者统一验收`。

`AUTHOR_FIRST_SPARSE_FOUNDATION_CLOSURE = 已实现并自动验证，待作者统一验收`：当前全部 Foundation 分类已使用同一小型显式字段展示元数据，核心字段默认展开、高级字段默认收起，已有高级/自定义值可发现、可编辑且收起保存不丢失；页面完成左分类、中条目、右详情/编辑布局，active_modules 只降低空的可选分类显著度，已有记录即使 profile 陈旧也始终可达。七种既有中央关系继续通过 RelationSelector 和稳定 ref 写入同一 ProjectModel.dependencies，没有新增关系类型或重复自由文本关系。人物恰好选择一个、且该 system 有可解析 `levels_stages` 时，`current_level` 使用真实选项下拉并保留不匹配旧值；没有阶段 ID/实体。Story Map 已可直接用共享编辑器新增人物/关系，同项目保存刷新保留图面，Cytoscape 使用原生换行把头像、姓名和一句话介绍居中堆叠。fixture 自动化已机械证明稀疏 author write、ProjectData 显式关系投影、Context 对 system/组织/`current_level` 的消费、pending settlement 语义以及 FoundationDesign 只提议/确认必要分类和字段；没有改动生产后端闭环，也没有引入通用属性/Schema/ontology、KG/图数据库或新 AI runtime。真实连续作者/模型/文学效果仍不在自动验证结论内。

### 作者桌面体验与展示资产不变量（DESKTOP_UI_AUTHOR_EXPERIENCE_CONVERGENCE）

旧 UI 预览图只作为视觉与信息层级参考；当前 `main` 的真实能力、authority、Bridge、Agent、Knowledge 与作者操作合同才是功能真相。不得为了还原预览恢复 Mock 数据、旧功能假设或第二套状态；优先实现真实 UI 后由作者查看实际桌面效果再精修。

人物头像、作品封面与界面装饰插图均为 **presentation assets**，不是人物、关系、Story State、Canon、future plan 或 Knowledge。上传、替换、恢复图片只按稳定 `project_id` / `source_ref` 绑定；不进入 author semantic change ledger，不触发「更新作品状态」，不调用 Direct AI 或 Agent。

- 人物可绑定作者上传的本地头像；无头像显示中性默认图形，绝不以姓名首字或 initials 冒充头像。Foundation 与 Story Map 消费同一绑定；姓名与 `one_line_intro` 始终来自同一人物 authority，并由同一 CharacterEditor 编辑。
- Story Map 人物节点固定为“头像 → 姓名 → 一句话介绍”，居中且头像明显大于旧节点；主体不塞完整档案。hover 只按“人物 / 当前状态 / 人物核心 / 背景与其他”展示已有作者可读字段，绝不显示 ref、revision、hash、token 或 provenance。
- Story Map 人物与关系编辑复用 Foundation 的 CharacterEditor / RelationshipEditor 及同一 author_edit/writeback。边是可选的关系编辑入口，没有 graph-local relationship state。
- 当前一次 Story Map 停留内，拖动位置在普通数据刷新与保存后保留；离开地图、切换正式项目或显式“恢复默认布局”才丢弃。坐标不是作品事实，绝不持久化。提供放大、缩小、适应视图、恢复默认布局；滚轮缩放应即时可用。“锁定布局”仅指节点视觉层级稳定，不禁止拖动。
- 统一展示资产能力仅有一套：项目范围的 cover、按稳定 source_ref 的 character avatar，以及全局 city / mountains / desk 插图槽。均经共享本地图片选择、校验、受管复制、持久绑定、替换与单槽恢复默认；元数据不保存源绝对路径或图片正文，前端不接收任意 file:// 路径。

### 当前产品收敛子阶段（2026-09-01，前瞻规则）

真实作者使用已经证明：Go Write 的 authority / Context / Knowledge / Author Operations / 作者触发语义刷新等底层能力已较完整，但“自动化回归通过”尚不等于“作者桌面可稳定日用”。当前 `REAL_WRITING_USAGE` 内进入 `DESKTOP_UI_PRODUCT_CONVERGENCE` 子阶段；本阶段的任务不是继续堆功能，而是把已经存在的能力收敛成稳定、清楚、单一职责的作者工作台。

优先级固定为：

`桌面启动可靠性与可诊断性 → Settings 信息架构 → 六页作者任务职责收敛 → 真实作品连续使用验收 → 再决定新增能力`

退出本阶段前执行以下长期约束：

1. **作者桌面启动是 P0 验收，不以 checker/build/pytest 代替。** 作者双击正式入口后必须稳定出现 Go Write；若失败，必须留下可持久读取的本地诊断证据，不允许“进程没窗口、黑窗一闪而过、只能靠开发者复现”成为正式使用方式。2026-09-01 作者在当时 `main` 双击 `启动Go Write.bat` 后没有出现可见窗口，故桌面 runtime 仍属于“已实现待真实作者验收/当前阻塞”，不得写成 DONE；具体根因必须由后续诊断证明，不能凭静态代码猜测。
2. **一个作者任务只有一个主要操作面，但唯一 authority 不等于唯一 UI 入口。** 同一原始数据只允许一个 authority owner、一套保存/校验/writeback 实现；在最适合作者操作的上下文中可以复用共享编辑组件、Controller 与 Author Operation。其他页面不得复制第二套业务状态、编辑器业务逻辑或写入路径；删除重复实现优先于重新排版重复入口。
3. **六页 ownership 固定：**作品概览负责重新进入作品所需的简介、方向/读者期待、进度、有效规划摘要、重要未解决项与一个主要下一步；作品地基（Foundation）是人物/关系/世界/地点/组织/system/故事线/伏笔等源记录的主要管理面；大纲与规划管理 future planning、篇幅/卷或阶段/章节细纲与 StoryPlan；正文管理管理章节正文与写作协作；故事地图是同一项目 authority 的派生查看/查询面，并可直接复用 Foundation 的共享编辑器和同一写入路径；作品检查只做 advisory 诊断。跨页交接与共享编辑可以存在，但不能形成第二套业务面。
4. **概览不是第二套导航。** 概览可以给一个最值得做的主动作和少量下一步建议，但不得把六页顶部导航完整复制成另一组同权重按钮；同一目的（例如“继续写作/正在写”）不得在同一屏重复出现多个主要入口。
5. **Settings 只暴露真实配置与必要诊断。** 同一环境/Agent/模型事实只展示一次主要视图；同一个“重新检测”只保留一个主要入口；AI 服务/API、Agent、执行方式应按作者实际配置任务组织，而不是按历史实现层重复分区。真实持久配置和 session-only UI 偏好必须明确区分，session-only 内容不得伪装为可持久“设置”。执行审计属于诊断，不与配置混成同一信息层。
6. **`更新作品状态` backend 合同不重做，只收敛呈现。** 项目栏保持唯一例行语义刷新入口和紧凑状态；待确认语义后果不得在所有作品页共用顶栏中展开成大块业务内容，详细内容进入独立详情层（drawer/modal/等价轻量层），确认仍复用现有 `prepare/get/confirm project state refresh` 合同。
7. **Story Map 保持派生面。** 图、时间线、未解决线索只消费同一 ProjectData/authority；人物、关系等可在地图上下文中直接复用 Foundation 已有共享编辑器和同一 author_edit/writeback 路径。Story Map 不得维护 graph-local 编辑逻辑、第二套 story state 或 database。
8. **先职责，后视觉。** 本阶段不是“换主题/美化”项目；先删除重复 ownership、重复按钮、重复状态与虚假设置，再做必要的布局密度、层级和响应式调整。不得为了视觉收敛重写冻结 StoryPlan/StoryWrite/Context/Knowledge/authority 架构。
9. **文档状态必须四分。** 后续 README / 当前状态 / 手册对能力统一使用：`已实现并验证`、`已实现待真实作者验收`、`已批准但未实现`、`历史记录`。技术路线（例如未来计划采用的编辑器/组件）若当前依赖和代码尚不存在，只能写作规划，不得写成已落地选型事实。
10. **新增能力冻结条件。** 桌面启动、Settings、六页职责和真实连续使用没有收敛前，原则上不新增作者侧大功能，不新增大型 runtime；只有当前收敛任务直接证明必须补的最小能力例外。现有能力能通过删除重复、重定向入口或小型根修解决时，优先不建新模块。

## 1. 项目定位

Go Write（仓库名 AI-Write）是作者主导、AI 辅助的中文长篇小说创作工作台。不是一键自动写整本书，也不是只会服从修改指令的文字工具。

创作流程：`参考/研究 → 构思 → 规划 → 写 → 审阅 → 修改`

理想体验：工作台准备状态与知识 → AI 生成/修改 → 独立诊断 → 作者反馈 → 针对性修订 → 作者接受 → State 结算 → 下一轮。作者不需要理解 Schema、手动挑 Skill、维护状态表。

## 2. 核心原则

### Borrow-first

真实问题 → 查成熟上游 → 最小真实测试 → 能借就借 → 只补剩余缺口。自研集中在：协议、路由、胶水、BKP、中文长篇适配、作者控制、Author Operations、Agent Adapter、Bridge、Task Manager、UI Views。

许可与复用规则：
- 成熟技术不重新验证；能直接使用成熟 MIT/BSD/Apache 等宽松许可组件时优先使用。
- 同类 AGPL/GPL 项目主要借架构、产品思路、交互设计。
- 复制具体代码前必须再次核验对应版本/文件的许可证。
- 不要因为 GitHub 有代码就自动复制。

### 案例只暴露问题，不决定架构

单个章节或漏检不能直接升级成长期 Schema / Skill。回到完整能力地图和成熟上游判断系统性缺口。

### CAPABILITY_FIRST_CONSUMER_DRIVEN

最终作者可感知工作台能力优先于单个子系统完善度。子系统达到最小合同并经过真实验证后默认冻结；后续缺口由真实下游消费者暴露。

开发决策规则：只有同时满足（1）真实正文/真实使用暴露问题；（2）问题重复或严重；（3）现有能力不能低成本解决；（4）新代码能明显降低长期负担，才允许新 runtime。否则 DO_NOT_BUILD。

窄口径更新：`THIN_ORCHESTRATION_BUILD_ALLOWED`——只允许复用现有合同的薄操作层（消除已两轮重复出现的机械摇柄）；不代表完整通用 Writer platform 获批（AI-write 作者侧桌面工作台 1.0 已批准进入实现）；不允许新 Final Schema；不重开 StoryPlan / Context Compiler / BookDistill。唯一已授权例外（2026-08-27）：KnowledgeRetrieve 为方法知识资产生命周期升级为统一多源检索入口（仅身份/目录泛化 + 最小选择管道，不引入向量库/模型调用/路由器）。

### 参考知识与原创事实必须隔离

- BKP：参考作品中提炼出的写作知识、模式、观察和边界
- Canon / Story State：我们自己正在创作的小说中已确定/已发生的事实与状态

自己的小说事实和作者要求始终高于参考作品建议。参考书只能提供方法和启发，不能污染或覆盖原创作品 Canon。

### 外部资料来源分层：作品案例与方法论资料

成品小说/剧本/影视作品，与写作、编剧、导演、剪辑、戏剧、表演等方法类非虚构资料，不按同一种知识来源处理。

- 成品作品主要提供 Observation / Pattern / Evidence、案例与适用边界；默认属于 source-bound BKP，不因表现优秀自动升级为 Skill。
- 方法类资料若明确给出原理、适用条件、步骤、检查项、失败模式或决策标准，其内容可以成为 `SKILL_CANDIDATE`；这类知识通常比从成品作品反推规律更接近可执行能力。
- `SKILL_CANDIDATE != Skill`。只有经过真实创作反复验证，形成稳定的输入 / 判断 / 步骤 / 输出边界，并满足 `CAPABILITY_FIRST_CONSUMER_DRIVEN` 的新增条件时，才允许进入 `05_Skills与自动化`。
- 成品作品可以作为方法/Skill 的案例、证据、反例与边界补充；方法书也不能因作者声称有效就自动获得 runtime authority。
- 潜在来源包括小说写作、编剧、导演、剪辑、戏剧、表演、摄影/构图、叙事心理、喜剧/悬疑、非虚构叙事、游戏叙事等；不因此预建新的分类系统。
- 外部资料的消化去向不止知识链一条：框架/产品参考、模板结构、案例语料、题材研究等各有归宿，见第 14 节资料消化多目的战略。
- MethodDistill 已于 2026-08-27 获批并实现（方法类资料的方法知识蒸馏，见第 13 节）；它产出的是来源绑定知识，不是已验证普适真理。自动 Skill 生成、模型治理或未来规模优化仍不开发：`capability_candidate=true` 仅表示潜在可执行的方法知识，绝不自动创建/晋升 05 侧 Skill；05 Skill 晋升仍是独立的、证据/测试驱动的人工过程。

### KNOWLEDGE_SHARED_AUTHORITY_ISOLATED

多部原创小说可以共享 `02_素材知识库` 与未来成熟的 `04_写作知识库`；但每部小说的 project_id、Author Intent、Story State、approved_plan、Decision、正式正文和项目专属资料必须完全隔离。

切换作品等于切换整套原创 project context；共享知识不等于共享原创 authority。

### 作者控制 ≠ 作者审批

重要创作方向由作者控制；机械工作后台自动完成。只有真正存在创作歧义、冲突或高风险不可逆操作时才需要作者确认。

### 基础模型创作能力优先

外部知识、BKP 和专业能力默认按需、稀疏、问题驱动地介入。0 个知识命中/采用是合法结果。

### 自由规划优先与 BKP 后置

E2-B 验证：强模型自由规划优先原则成立；BKP 后置策略得到支持。

### 作者侧产品原则

1. 后台按成熟作者标准工作，前台按普通新手能够理解的方式交流。
2. 日常创作界面中，作者操作作品和创作任务，不需要每次选择 Agent、模型或 Skill；「设置」页面允许作者真实配置 AI 服务/API、模型、Agent 与任务执行配置。Agent 是 AI-write 执行 Skills 和复用知识库的重要执行层。
3. 高频、明确动作优先按钮/菜单；模糊、创造性需求保留自然语言。
4. 模型与 Agent 能力差异进入后台路由，日常界面不默认暴露模型/Agent 选择器；不提前固定任务类别、默认模型-Agent 组合、自动路由或“省钱/平衡/高质量”模式，由以后实际配置决定。
5. AI 草稿/方案/分析默认都是候选；只有作者明确采用才进入正式 Authority。
6. AI 平时应克制，不持续打扰作者。
7. 系统应根据当前作品状态主动给出“接下来建议做什么”，但不能替作者偷偷做创作决定。
8. UI 与功能共同设计：真实作者行为 → UI 原型 → 反推后台能力，不再先独立堆功能。

## 7. REAL_PROJECT_WIRING 长期合同

### 7.1 作者输入合同

作者使用自然语言，不要求知道内部 Skill 名称，也不要求维护固定的 StoryDesign/StoryPlan/Context/KnowledgeRetrieve Prompt 模板。

常见表达可以是：

- `新建《作品名》。我现在的想法是……`
- `继续《作品名》。今天我想……`
- `切到《作品名》……`
- `基于已经确定的方向，规划……`
- `写下一章/下一场，我希望……`
- `这部分不要……改成……`
- `这个方向确定，就按这个走`
- `这版接受，定稿`

前六类属于自然任务描述；后两类涉及长期 authority，必须语义明确。类似“还行”“先这样看看”“差不多”不得自动升级为确认或 acceptance，不确定时只做一次最小澄清。

### 7.2 每部作品的私有边界

每部真实作品直接位于：

```text
03_作品工程/<作品名>/
├─ README.md
├─ 01_设定与人物/
├─ 02_规划/
├─ 03_正文/
├─ 04_资料与灵感/
└─ _工作台状态/
```

`_工作台状态/` 绑定现有 frozen runtime 的 `project_dir`，保存 Author Intent、Story State、Decision/authority 等 production state；Context、recent prose、临时 Brief 等仍是可重建派生物，不要求长期保存。

任何会修改正式正文、Story State、planning、Decision 的动作，都必须先唯一解析当前作品与 `project_id`。多作品存在而用户只说“继续写”时不得猜；用户明确说作品名时直接切换。

### 7.3 正文存储：章存储，scene/write-turn 运行

正式正文物理存储按章：

```text
03_正文/
├─ 第001章.md
├─ 第002章.md
└─ ...
```

只有作者明确接受的版本才进入 `03_正文`。

StoryWrite 运行和 production acceptance 继续使用稳定 `scene_ref` / write-turn ref。一个章节可以包含多个 accepted ref；如果用户一次写完整一章，也允许一个较大的 accepted unit。不得把 scene 变成强制文学层级。

REAL_PROJECT_WIRING 只需维护最小 accepted ref → 正文章节映射，使 `accepted_text:<scene_ref>` 可以追溯到实际正式正文。不要升级成数据库、正文知识图谱或复杂事件系统。

### 7.4 长篇上下文分层

每次写作不重新阅读全部正文。继续使用现有已验证结构：

1. Story State：长期连续性与 Canon 状态；
2. active approved_plan：未来方向；
3. ContextCompiler：只选择当前任务需要的少量 State；
4. recent prose：最近 accepted 正文末尾约 1000–2000 字，解决短距离文字连续性；
5. 旧正文：真实需要回溯具体原文时才定向读取对应章节；
6. BKP：明确 knowledge need 时少量调用；0 BKP 是正常路径。

当前禁止因为“将来可能有用”而提前建设原创正文全文 RAG、embedding、vector DB。若百万字级真实创作反复证明定向旧文查找成为稳定瓶颈，再由 consumer evidence 决定是否升级。

**长期上下文管理方向：**

- Go Write 是长期上下文/状态的唯一持有者；Agent 对话历史与 Agent 自动压缩（compaction）不是权威记忆。
- Agent 自动压缩只是兜底行为，不是 Go Write 正常的上下文管理方式。
- ContextCompiler 继续只提供小而显式、任务相关的 Context。
- 当前不建设复杂上下文窗口 UI 或 token 预算优化器；收集真实任务使用数据之前，不引入动态上下文预算。

### 7.5 多作品与共享知识

多本小说同时更新时：

- 每本书有独立 project_id / State / Planning /正文 / Decision；
- 切换作品必须重建该作品的当前 Context，上一作品 Context 不得继续沿用；
- 作品专属调查/灵感放 `03_作品工程/<作品>/04_资料与灵感/`；
- `02_素材知识库` 跨项目共享；未来 `04_写作知识库` 也可跨项目共享；
- BKP 永远只是参考知识，不因被某作品使用过而获得另一作品的 Canon authority。

**知识规模边界（source-bound BKP）：**

- source-bound BKP 卡片始终可单独追溯回其来源；
- 不因不同书籍的机制相似就物理合并/删除跨书卡片；
- 相似/重复知识堆积是检索排序与多样性问题，不是存储 authority 问题；
- 当前不建设 vector DB、知识图谱、全局去重或语义聚类；
- 多样性重排 / State Recall 只有在真实规模证明需要时，才作为未来 consumer 驱动的选项考虑。

### 7.6 正文 acceptance 生产链

冻结目标链：

`候选正文 → 作者明确接受 → 写入/更新对应章节 Markdown → 登记 accepted scene ref → mechanical settlement → 写回当前项目 production Story State → 下一轮从新 State + recent prose 继续`

未接受草稿不得进入正式正文；未接受正文不得触发 production settlement。`ambiguous` / `creative` settlement 候选仍不得写入 Story State。

## 8. Go Write 2.0 正式产品基线（PRODUCT_BASELINE = GO_WRITE_2_0_APPROVED）

Go Write 2.0 是面向中文长篇小说作者的通用创作工作台。它固定的是项目管理框架，不是把每部作品锁进固定大纲、卷章或资料结构；作品内的工作内容、阶段、规划粒度和资料组织必须可以随作者的实际任务动态生长。

### 8.1 稳定页面与产品能力

作品一级页面固定为：

`作品概览 / 作品地基 / 大纲与规划 / 正文管理 / 故事地图 / 作品检查`

页面职责围绕作品推进而非暴露内部 Skill、Schema 或 Agent：概览有限展示可持久作品简介/核心梗概、真实 Author Intent 的作品方向/读者期待、进度、当前有效规划摘要、重要未解决项，并只给一个主要继续动作；作品地基管理长期故事资料；大纲与规划管理 future planning 与篇幅结构；正文管理管理正式章节与写作协作；故事地图消费同一真相作图谱/时间/线索投影，并可复用地基共享编辑入口；作品检查保持 advisory、零 authority writeback。

字数规划是一级能力，使用可追溯链路：`总目标 → 可选卷/阶段预算 → 章节范围 → 正文实际字数`。卷/阶段与章节以稳定 ref 关联；作者可以不分卷，全书 `chapter_number` 始终连续，规划和正文管理共享同一章号。本节确立产品方向与验收边界；除已有运行时能力外，不将上述 Go Write 2.0 页面、简介/核心梗概持久化、动态内容结构或字数规划表述为已实现。

列表型工作区（卷/阶段、章节列表等）应有稳定可视区域，超出后只在该列表区域内部滚动；drawer 固定头尾、正文区独立滚动。不得机械给所有卡片固定高度，也不得制造多层嵌套滚动；布局只在真实作者任务需要处引入滚动责任。

**运行时稳定性（2026-08-31）：** P0 空白页根因是桌面默认加载未校验的旧 `ui/dist`，旧前端与新后端混用后对缺失的 `length_plan.actual_total_words` 直接解引用。构建现写入前后端源码指纹，桌面壳拒绝不一致的构建；`ProjectData` 在共享 Bridge 边界完整校验，六页挂载烟测与项目内容区 Error Boundary 已覆盖，桌面人工验收仍待执行。

### 8.2 Authority 与既有技术地基

AI 生成的 candidate、draft、proposal 默认非权威，只有作者明确接受才可进入正式正文、Story State、Decision 或 approved_plan。未来规划永远不等于 Canon。作者修改已确定事实、规划或正文时，必须先做影响分析并按既有 authority/writeback 合同安全处理，不允许绕过合同直接改写 Canon。

唯一 authority / 单一写入实现不限制作者侧只能有一个编辑入口：多处入口可在不同上下文复用同一 Foundation 编辑组件、Controller、Author Operation 与校验/writeback 合同；它们不得拥有第二份页面状态、领域逻辑或保存实现。

Go Write 2.0 继续复用并保护现有技术地基：ProjectWorkspace、StoryPlan、StoryWrite、ContextCompiler、KnowledgeRetrieve、BookDistill、MethodPrepare / MethodDistill、AuthorTaskCoordinator、Qoder bridge、execution audit 与 project_id 隔离。产品基线不授权重构这些冻结合同，也不把未验证的 Go Write 2.0 能力标记为 DONE。

### 8.3 Go Write 端到端职责与统一变更合同（GO_WRITE_V2_PRODUCT_CONTRACT）

本节是 Go Write 2.0 的稳定产品合同。后续页面实现、后端扩展与未来里程碑均以本节为准；与本文历史表述冲突时以本节为准。

**A. 端到端职责（四层一体）**

1. 知识生产：参考作品走 `SourcePrepare → BookDistill → 来源绑定 BKP`；写作/编剧/导演/剪辑/戏剧/表演等方法源走 `MethodPrepare → MethodDistill → 来源绑定方法知识`；入库/提纯/蒸馏均为作者显式动作；`SKILL_CANDIDATE` 不自动晋升 Skill，方法源不自动进入 04。
2. 创作时知识调用：规划/写作/检查通过统一 `KnowledgeRetrieve` 按需请求知识；检索稀疏、问题驱动，从属于作者当前决定与项目自身 authority；作者日常创作不手动选择 BKP/Skill/Context。
3. 创作管理：idea → project → foundation → 篇幅/阶段/故事/章节规划 → 写作 → 检查 → 修改 → 接受 → 继续；多项目隔离、作者确认、accepted 正文、active planning、任务执行与项目状态由 Go Write 管理。
4. 全书连续性：正文/地基/规划的变更最终收敛到同一当前项目理解；后续 AI 任务必须消费最新有效作者意图、已接受事实/状态、active planning 与相关近期正文；六个页面是同一作品的视图/动作，不是六个独立事实仓库。

**B. 统一变更循环（目标合同；未完整实现，不得标记 DONE）**

`作者编辑/接受 → 记录 delta → 确定性处理 → 需要时 AI 语义结算 → 经安全合同更新权威/当前项目状态 → 重建派生视图 → 下一个 AI 任务读取最新有效状态`

- 确定性代码处理计数、排序、显式引用、显式日期/时长、版本号等机械可证变更；
- AI 处理关系变化、事件含义、伏笔、时间语义、人物/世界状态后果、规划影响等语义解释；
- 不确定的 AI 结论保留为待作者确认的 candidate；AI 不得因不确定推断静默改写无关正文/规划/Canon；
- 日常工作增量、定向；整书重读/校准仅用于初始导入、大修改、阶段收尾或检测到不一致。

**C. 时间是一等故事状态**

时间不仅是 Story Map 可视化，而是当前故事状态的一部分：绝对时间锚点（仅当显式已知）、相对时间变化、事件顺序、经过时长、叙事顺序与故事时间的区分、显式循环日历标记。不得从相对文本臆造绝对年份；确定性日期/时长计算属于代码（在时间语义被识别后）；闪回、timeskip、相对时长、循环节日/季节、模糊时间表述的语义识别属于 AI；时间变化可能影响年龄、经历、事件顺序、关系/世界状态与未来规划。不建独立时间数据库。

**D. 页面职责合同（六页六个作者任务，互不重复）**

- 作品概览：作者重新进入作品的有限摘要与一个主要继续动作；展示作品简介/核心梗概、方向/读者期待、进度、有效规划摘要和重要未解决项，但不复制完整地基、规划、地图或顶部导航。
- 作品地基：人物/关系/世界设定/地点-组织-system/故事线/伏笔/悬疑等的源表示与主要管理面；不把事件史/未解决线索当主体；无 raw JSON/debug 表示。
- 大纲与规划：future planning（active 方向、总篇幅、可选卷/阶段、连续章号的章节细纲）；保留真实 StoryPlan candidate/confirm 生命周期；卷/阶段与章节使用稳定 ref 关联，不强制分卷，不建立第二章节系统或第二聊天面。
- 正文管理：与规划共用 `chapter_number` 的章节/正式正文工作与 AI 写作协作；保留当前真实 StoryWrite authority 流程。
- 故事地图：派生可视化/查询——人物关系图、时间与事件、未解决线索（含受支持时的伏笔）；绝不是第二个地基数据库。它可以直接复用 Foundation 的共享人物/关系编辑器和同一 author_edit/writeback 路径，但不拥有 graph-local 事实、编辑业务逻辑或第二写入实现。
- 作品检查：仅诊断；结果 advisory、零写回、无第二权威。

规则：同一原始列表不得仅因数据可得就在多页重复呈现；共享编辑入口必须复用同一 authority owner 与写入实现。Foundation 拥有关系事实的源表示，Story Map 将其消费为可视化；无法形成连线的关系记录如实以紧凑区块呈现，不猜测、不隐藏。

**E. 作者自由编辑目标（未来里程碑；不得伪造）**

作者对正文/地基/规划的自由编辑是 Go Write 2.0 核心要求；UI 不得强迫所有变更走聊天。作者编辑后，AI 辅助增量结算更新受影响的当前状态与未来上下文，后续写作/规划必须消费这些更新。该要求必须走安全 authority/writeback/invalidation 合同；接入完成前 UI 不得显示假编辑或假同步控件。

**F. 可运行 UI 验收原则**

作者验收在可运行作者 UI 中进行，而不是读代码；改变作者工作流的 backend-only 里程碑在没有真实 UI consumer 前不算完整；不得仅为预览完整而展示假控件。

### 8.4 长篇小说领域模型与上下文闭环（NOVEL_DOMAIN_MODEL_CONTRACT）

本节是 Go Write 2.0 唯一权威的 Novel Domain Model 合同。领域模型是现有每项目作者工作区与 production Story State 的稳定应用边界，不是第二套 Story State、数据库或 AI 生成 Schema。六个作者页面、StoryPlan 投影、统一变更结算和 Story Map 都消费同一项目隔离模型；派生快照、图谱、Context 与摘要均不获得独立 authority。

**A. 稳定对象与项目配置**

- 稳定对象类型：`character / relationship / world_setting / location / organization / system / storyline / foreshadowing / event / mystery_information / chapter_fine_outline / chapter_actual_result`；篇幅阶段与显式依赖仍复用当前 project-model 对象/边，不固定 book/volume/arc 层级。
- 项目保存一个小型 `story_bible_profile` 配置：`genre_tags`、明确已知时的 `narrative_mode`、`active_modules`、可选作者字段配置。它只决定作者面显示与允许的可选字段，不复制领域事实；隐藏模块绝不删除数据，AI 文本绝不生成数据库 Schema。
- `work_direction / reader_promise / hard_constraints / open_space` 保留为真实 Author Intent，继续供 StoryPlan、StoryWrite 与 Context 消费；作者面将其集中在作品概览。作品简介/核心梗概应以最小、可持久、作者可编辑的既有 Author Intent 或项目工件承接，不新建第二简介库；这是前瞻要求，未实现前不得标记 DONE。
- 默认模块：core、characters、relationships、world、locations、organizations、storylines、foreshadowing、events、time。标准可选模块：power_progression、career_rank、economy_resources、politics_factions、technology、supernatural_rules、romance_social、mystery_information、custom。
- 固定核心字段提供跨作品稳定语义；可选模块与作者自定义字段按当前作品启用、允许为空。UI 只显示已填充的有意义字段，不暴露 ref、revision、authority/provenance、执行 token/ID 等内部元数据。

**B. 人物、关系与人物摘要**

- 人物稳定核心字段：name、aliases、one_line_intro、role_identity、position_title、faction_org、visible_traits、persona_core、goal_desire、fear_weakness、inner_conflict、values_beliefs、background_summary、speech_style、behavior_anchors、secrets、current_state、current_objective、arc_stage、notes；除 name 外均可按作品实际填写，不用巨型必填表。
- 人物可选字段包括年龄/年龄状态、当前位置、武力/等级、成长/修炼级别、职业/职级、财富/资源、特殊能力、社会/声誉状态、悬疑信息、所引用 system 与当前级别/状态，以及作者配置的自定义字段。
- 人物卡显示作者绑定头像或中性默认图形、姓名、一句话介绍、必要 current/future 状态；详情只显示已填充的特征、人设、背景、等级、职位/身份、当前状态、核心目标、说话/行为特点等。头像是独立 presentation asset，不写入人物语义字段；Foundation 与 Story Map 编辑同一 underlying record。
- AI 维护人物摘要必须走统一增量语义结算，只更新本次变更真正影响的人物；可补丁字段限于当前变更与相关快照有证据支持的 one_line_intro、visible_traits、persona_core、background_summary、position_title、power_rank、current_state、current_objective、arc_stage、speech_style、behavior_anchors。不得整组重写、补造履历/武力/职位；显式作者字段永远优先于 AI 摘要补丁。
- 旧 Story State 的人物身份只接受显式 ID/name。自由状态句是 observation，不得成为人物 identity；可唯一解析的 observation 附着到有效人物，无法解析的旧状态只保留为历史/诊断证据，不进入图谱。作者工作区人物 supersede 旧身份时只能形成一个有效节点。
- 关系是具有两个稳定显式人物端点的单一 editable edge：label/type、current_state、relationship_phase、key_history、current_tension、可选 trust/closeness、hidden_information、notes 与 current/future。Story Map 不拥有 graph-local 关系数据。

**C. 世界、地点、组织、通用系统与故事线**

- world_setting 可按需保存时代/时间背景、地理范围、社会结构、政治秩序、经济/资源、文化习俗、科技水平、超自然基线、重要历史、硬规则、禁忌、已知例外、与故事相关的约束和备注；不要求每部作品填写全部字段。
- location 字段：name、type、region/parent、physical_features、story_social_function、明确时的 controlling_organization、rules_risks、current_state。
- organization 字段：name、type、purpose、hierarchy、leader_key_members、resources、territory_scope、rules、external_relationships、current_state。
- `system` 是唯一通用等级/规则域，可表示武力、修炼、魔法、职业、晋升、军政职级、声誉、财富经济、科技访问或作者自定义层级；字段为 name/type、purpose、levels_stages、entry_progression_requirements、abilities_privileges、limitations_costs、visible_markers、exceptions、important_rules、notes。不得硬编码修炼模型或新增题材 Skill。
- storyline 字段：title、goal_purpose、stakes、main_conflict、participating_characters、related_organizations_locations、stage_progress、dependencies、expected_payoff_end_condition、current/future。

**D. 伏笔、信息、事件与一等时间**

- 伏笔/承诺/未解线采用 `setup_trigger → reader_question_promise → related_entities → state → intended_payoff → actual_payoff`；state 只允许 planned、planted/open、paid_off/resolved、显式选择后的 retired/abandoned。AI 只有在正文或作者决定支持时才能推进状态。
- mystery_information 仅在项目模块启用时保存 secret/fact、who_knows、who_does_not_know、明确的 mistaken_beliefs、reveal_status、planned_reveal、actual_reveal_event_chapter；不默认启用。
- event 字段：title、participants、location、cause、what_happened、result、impact、明确时的 story_time_anchor、明确时的 relative_time_movement、narrative_chapter_order、current/future。
- 时间保持绝对锚点（仅显式）、相对时长、事件顺序、经过时长、叙事顺序与故事时间的区别、循环日历标记。AI 识别时间语义；只有明确 ISO 基点与结构化 `relative_duration {value, unit}` 同时存在时，代码才写出 `computed_story_time_anchor`，纯相对文本只保留、不计算；不得从相对语言发明绝对年月日，不建独立时间库。

**E. 当前事实、未来规划、细纲与实际章节结果**

- current 是已接受正文/生产状态/作者明确当前事实；future 是已确认 planning。StoryPlan candidate 未确认不写任何 authority；确认后，同一次 Agent 结果可投影 profile/module、人物、关系、世界、系统、地点、组织、故事线、伏笔、规划事件与细纲，但全部显式 future/planned 对象仍不是当前 Canon。
- 推荐规划顺序仅作指导，不是强制 wizard：1）前提/题材/读者承诺/基调/叙事方式；2）世界基线与硬规则；3）项目领域 profile；4）主角与核心人物；5）核心关系；6）相关地点/组织/system；7）主冲突、故事线与主要承诺/伏笔；8）总篇幅及可选阶段/卷/弧；9）章节细纲；10）正文。作者可从后层开始或回改前层；缺项只提示，不做无必要硬阻塞。
- chapter_fine_outline 是写作意图：章号/标题、目标最小/最大字数、章节目的/任务、可用时的上一章实际回顾、planned synopsis、相关时的 POV、规划地点/时间、参与/新人物、关键 beats/events、冲突、情绪变化、信息释放/信息差、伏笔埋设/回收、结束状态/hook、故事线/阶段、作者备注，以及代码确定的 actual word count。
- 卷/阶段与章节用稳定 ref 关联，而非仅靠自由文本标签；卷/阶段可为空。全书 `chapter_number` 连续顺延，规划章节与正文管理中的同一 `chapter_number` 是同一章节身份。删除未产生正式正文的 future 章节可删除/退役其规划；已有正式正文不得由大纲页顺手删除或覆盖，正文删除/归档须使用明确高风险合同。
- chapter_actual_result 是已接受正文现实，始终与细纲分开：短实际摘要、实际重要事件、涉及人物、人物状态变化、关系变化、实际时间变化、地点/状态变化、已揭示信息、实际埋设/回收伏笔、未解线、章节终态、与细纲的偏差。accepted AI 正文或手动正文保存并同步后只更新对应章节实际结果，不覆盖细纲。
- 正文与细纲发生实质偏差时不强迫正文回到细纲、不静默重写未来规划；只生成简短 planning-impact candidate，作者确认后才改未来 planning。

**F. 统一编辑、结算与重校准**

所有 Foundation、关系、世界/system/地点/组织、Story Map shared editor、规划/细纲、accepted AI 正文、手动正文、作者确认的检查/规划决定只走一条路径：

`durable edit/accept → delta → deterministic processing → targeted semantic settlement when needed → effective domain objects / chapter actual result → derived views → next AI task reads latest state`

纯显示/机械变更可确定性同步；对人物、关系、世界规则、system、故事线、伏笔、事件、时间或细纲有语义影响的 Foundation 变更必须进入定向结算。durable 作者编辑即使结算失败也保留并优先；不建 CharacterSync、RelationshipSync、WorldSync、TimeSync、ForeshadowSync、OutlineSync。日常变更只结算受影响实体；初始导入、重大手动重写、阶段/卷结束、作者显式全书检查或检测到不一致时才允许更广校准，禁止常驻全书 AI。

Review 可提出人物/关系不一致、世界/system 违规、时间矛盾、遗忘伏笔、细纲/正文偏差与连续性问题，但始终 advisory；作者接受修正后重新进入上述统一路径。

**G. 长篇 Context 与知识使用**

- 正常规划/写作不读全书。task-near 必含作者指令、作品承诺/意图、当前章细纲、上一章 actual result、近期 accepted prose；结构化状态只选当前/受影响人物与关系、世界/system 规则、组织/地点、事件/时间、故事线、开放伏笔/线索和相关未来规划。
- 旧正文/全文只用于定向证据回查、作者显式检查、重大重校准或结构化状态不足；ContextCompiler 保持显式 selection，空 selection 永不 fallback 全 State，并由代码执行项目隔离、stale guard 与 context-size limit。
- 规划/写作/检查及相关 Foundation 设计 AI 可表达 knowledge_needs（人物塑造、行动细节、对白声线、关系张力、世界构建、成长系统、结构、节奏、悬念、伏笔回收、章首章尾、冲突、信息控制等）。空 needs 不检索；非空 needs 只调用现有统一混合 KnowledgeRetrieve，一次包同时覆盖 reference_bkp / method_source / validated_knowledge；外部知识始终 advisory。
- 人物塑造不是字段堆积。写作 Context 将人物可复用 anchors（可见特征、行为锚点、说话方式、内在矛盾、目标/恐惧、关系特异反应、当前压力）与场景/章节目的、关系语境、选择性检索知识结合，提示通过行动、对白、选择、反应、对比和具体细节呈现人物，不硬编码单一文学理论。

**H. Code / AI / Agent / Skill 边界**

- Code：ID/ref、持久化与 project isolation、版本/哈希/原子写、字数、显式依赖边、语义识别后的日期/时长计算、图谱投影、current/future 过滤、stale guard、确定性 invalidation、Context 大小限制。
- AI：语义抽取、人物/人设摘要、关系与事件含义、时间解释、伏笔解释、世界/system 影响、细纲偏差含义、planning impact、相关 Context 选择、检索知识应用；只允许输出有证据的补丁与待确认候选。
- Agent：在 Settings 指定的模式下承载规划、写作与结算 AI 任务；Agent 对话历史不是项目 authority。
- Skills：仅保留已有且经证明的 SourcePrepare、BookDistill、MethodPrepare、MethodDistill、KnowledgeRetrieve、StoryPlan、StoryWrite、ContextCompiler、ProjectWorkspace 等稳定工作流；禁止 CharacterSkill、WorldSkill、RelationshipSkill、ForeshadowSkill、PowerSystemSkill。

## 11. 执行架构与 Agent 交互长期原则

> 前瞻执行边界以 §15（Code / Direct AI / Agent / Skill / Author）为准。本节保留的实现记录对未迁移路径仍然有效；高频语义结算已按 §15 迁移到 Direct AI，不再经由 Agent 执行层（实现事实见 §17）。

### 11.1 角色分工

- **Go Write** 是作者侧工作台和长期状态持有者。管理作品、Story State、planning、知识库、素材资产。
- **Agent 执行层**（当前生产绑定为 Qoder Desktop `/gowrite`）接收 Go Write 准备的任务，执行语义分析，返回候选结果；具体 Agent/模型由 Settings 配置（见 11.8 / 11.9）。

### 11.2 当前 Token Plan 作者路径

```
Go Write 准备 pending task
→ 尽力把 Qoder 桌面端切到前台（AppActivate，不模拟键盘）
→ 作者在自己准备好的 Qoder 对话输入 /gowrite
→ Qoder 执行，写回 response
→ Go Write 严格验收（合法 JSON + schema 校验）
```

### 11.3 Qoder 会话原则

- 可以为正在创作的作品/工作保留一个「Go Write 执行器」会话
- 一个执行器会话可连续使用多轮（不同任务）
- 上下文过长时直接换一个新的执行器会话
- 新会话不需要继承旧聊天历史——真正上下文由 Go Write 每轮重新准备
- 不要求迁移旧 Qoder 对话历史

**长期原则：Go Write 管长期记忆和上下文。Qoder 对话只负责当前任务执行。Qoder 对话不是 Canon / Story State / planning 的来源。**

### 11.4 不为 Qoder 对话开发管理系统

当前不需要：
- 自动找到「正确的」Qoder 对话
- Deeplink 自动创建新对话
- workspace 自动切换
- Qoder 会话历史持久化或检索

Go Write 只做：准备任务 → 尽力切前台 → 作者自己操作。

### 11.5 后台模型调用原则

- 普通 pytest / build / 启动 / 读取设置：**0 次真实模型调用**
- 真实模型测试必须显式人工 opt-in（如 `GOWRITE_REAL_QODER_TEST=1`）
- Settings「测试连接」只验证本机执行入口与当前配置（不调用模型或远端服务）；真实模型调用只发生在显式开启的测试路径

### 11.6 已验证事实

- 新建作品纵切 PASS（「两条狗」案例）
- 换干净 Qoder 会话仍可执行（Qoder 历史不是长期上下文来源）
- 默认 pytest 0 次真实模型调用
- Deeplink / 自动 Qoder 会话管理不进入长期架构（已撤销）

### 11.7 案例只暴露问题，不决定架构原则

本次 Deeplink 实验暴露了「不需要自动管理 Qoder 对话」的事实。
不因此建立新的自动化原则。继续按 11.4 执行。

### 11.8 作者日常创作禁止隐藏调用真实 AI（2026-08-20）

**原则：作者在 Go Write 日常创作时，不得后台偷偷调用未配置的模型/Agent 路径。**

#### 当前已验证执行边界

- Settings 支持显式的「交互桥（Interactive Bridge）/ 直连（Direct）」执行配置，保存时校验所选 Agent 与模型在当前发现结果中真实可用。
- Agent/模型发现与内置/自定义模型配置属于 Settings。
- `/gowrite` 命令的安装/就绪检测已修复并验证（安装/修复入口 + `command_ready` / `bridge_ready`）。
- 现有生产 StoryPlan Author Operation 仍接 Qoder Desktop `/gowrite`：Go Write 准备任务 → 作者在 Qoder 桌面端执行 /gowrite → Qoder 返回结果 → Go Write 严格验收。
- Settings 保存的 Direct Agent/模型选择尚未绑定到生产 Author Operations（属 P1）。
- 未来作者显式选择的 Direct 模式不是"隐藏 AI 调用"；隐藏的、未配置的模型调用仍然禁止。

#### Agent 角色分类（必须分开）

| 角色 | 谁启动 | 用途 | 日常作者流程参与 |
|---|---|---|---|
| 开发 Agent | 用户主动打开 | 用 Qoder / DeepSeek 做代码开发 | 否 |
| 作者执行 Agent | /gowrite 桥（Qoder 桌面端，当前生产绑定） | 当前作者创作执行路径 | **是** |
| 测试 Agent | 显式 opt-in（真实模型测试需显式开启 / 测试连接按钮） | 连通性验证 | 否 |

#### 关键规则

1. 后台执行能力代码可以保留，但不能被普通作者按钮偷偷调用。
2. 同一个软件（如 Qoder）可以承担多个角色，但角色不能混用。
3. 未配置的模型调用一律禁止；真实模型测试必须显式 opt-in。
4. StoryWrite 两阶段逻辑暂时保留，不因本次收敛重构；待 StoryPlan 真实作者纵切通过后单独处理。
5. Settings 中的执行模式 / Agent / 模型选择已绑定到生产 Author Operations（StoryPlan / StoryWrite / NewProject / Review 的 Direct 路径均由 Settings 决定）；Interactive（/gowrite）用于已接入交互桥的操作（NewProject / StoryPlan / StoryWrite 两阶段桥），Review 当前仅 Direct、绝不回退。

### 12.1 新建作品“正在打开作品”卡死 —— 根因与修复

**根因（前端 stale-closure）**：`ProjectsPage.confirmNew` 在 `await np.confirm()` 之后读取**本次渲染闭包**里的 `np.state.confirmed?.project_id`。`confirm()` 内部是异步 setState，闭包里的 `confirmed` 必然还是 `null` → `projectId` 为 null → 不关闭对话框、不 reload、不打开 → UI 永远停留在“作品已创建，正在打开…”。

**修复**：`useNewProjectController.confirm()` 改为返回 `Promise<ConfirmResult | null>`；页面用返回值驱动 `setShowNew(false) → reload() → openProjectById(confirmed.project_id) → setProjectSection('overview')`，不再依赖 setState 后的旧闭包状态。后端 confirm→list→open 链已有自动化覆盖（`test_new_project_readable_by_existing_chain`）。

### 12.2 Settings：持久化配置与能力发现分离

- 后端拆分为“读已保存设置 + last-known 发现快照”（进程内缓存，只有首次无快照或显式“重新检测”才执行发现）；新增 `discover_agent_environment` 桥方法（强制刷新并更新缓存）；

## 14. 资料消化多目的战略：价值优先、格式其次（2026-08-29）

基于对历史写作资料库（7451 文件 / 约 64.7GB，仓库外目录）的一次完整内容审计落地。审计结论与永久规则如下；完整证据在库外审计工作区（`写作素材包\_GoWrite资料消化_2026-08-29`），本手册只留原则。

### 14.1 资料消化有多个目的，不是所有有价值资料都成为可检索知识

现行路由目的（暂行分类，非封闭，材料需要时可增改）：
- `FRAMEWORK_REFERENCE`：细纲/章纲/场景表/节拍表、人物卡/人物小传/人物关系/角色弧、世界观/组织势力/时间线、伏笔与回收/信息差/故事线表、分卷与字数预算、修改/检查/连续性维护工作流，以及编剧/导演/剪辑/戏剧/表演中可迁移到小说工作台的方法——它们影响 Go Write 的框架/页面/字段/数据组织设计，**不成为运行时知识**；
- `KNOWLEDGE_SOURCE`：可复用写作/编剧/叙事方法（来源绑定可检索知识候选）；
- `CASE_SOURCE`：作品/拆解/分析案例，主价值是观察、证据、模式、反例、边界，必须保持观察/证据/边界区分，不升格为通用规则；
- `TEMPLATE_REFERENCE`：表单/表格/检查单/卡片等结构本身有价值的资产，**不得压平为通用散文摘要**；
- `RESEARCH_REFERENCE`：服务于特定故事的事实/领域研究；
- `ARCHIVE_ONLY` / `LOW_VALUE_OR_DUPLICATE` / `MEDIA_DEFERRED`。

### 14.2 价值优先、格式其次（VALUE_FIRST_FORMAT_SECOND）

先判定高价值资产与其用途，再只批处理选中的格式。不因为“格式能解析”就批量转换低价值文件；不为了消化历史资料库而建设永久的全格式（DOCX/XLSX/PPTX/PDF）摄入 runtime；临时转换脚本属于工作区，不进产品代码。

### 14.3 结构保留与案例边界

- 模板/结构资产的字段、工作表、顺序、关系必须保留（结构即价值）；
- 案例资料保留观察/证据/边界区分，与 BKP_POSTHOC_SPARSE_PROBLEM_DRIVEN 一致；
- 高价值历史资料在适当时蒸馏为轻量 Markdown 资产，必须携带来源溯源（原始精确路径 + 转换说明），转换不改写内容。

### 14.4 媒体与扫描资料默认暂缓（MEDIA_DEFERRED_BY_DEFAULT）

视频/音频/图片/扫描版 PDF 默认只做轻量分诊（路径/文件名/元数据/页数/邻近上下文）；不做批量转录/OCR/视觉处理，除非日后某个小而具体的资产被证明异常重要且可低成本检查。

### 14.5 与既有管线的关系（不是万能去向）

`SourcePrepare / BookDistill / MethodPrepare / MethodDistill / KnowledgeRetrieve` 对已服务的来源类型（REFERENCE_WORK / METHOD_SOURCE）保持有效；但它们不是全部历史资产的唯一去向：框架参考资料不进知识管线；案例语料与题材研究留在库外本地；登记/蒸馏一律是作者显式动作，不批量。

### 14.6 下一产品阶段：Go Write 2.0 完整 UI 预览

本次审计之后的产品开发阶段是 **Go Write 2.0 完整 UI 预览**：基于真实已实现能力 + 审计得到的框架发现（细纲/字数预算/人设字段/伏笔跟踪/阶段节奏等），让作者视觉检查完整能力地图并纠偏产品方向，然后再继续更大范围的后端开发。预览阶段不扩展后端合同；未实现能力必须以“规划中”明确呈现，不得冒充已接线。审计输入：库外审计工作区 `08_下一阶段UI预览输入.md`。

- **本次自动验证**：直接受影响与现有小说领域聚焦后端测试 198 passed、1 skipped；前端 `npm run test:model` 28/28；`npm run build` 通过（仅保留 Vite 既有 chunk-size 警告）；零真实模型/API 调用，未启动桌面或 ComputerUse。

## 15. 执行边界：Code / Direct AI / Agent / Skill / Author（2026-08-31）

本节是当前权威执行边界。历史章节（含第 11 节）中凡隐含“所有语义 AI 任务都由 Agent 执行层承载”的表述与本节冲突时，以前瞻架构论以本节为准；历史章节保留为实现记录，不重写。

### 15.1 根原则：最小实现，效果优先

Go Write 不追求“架构漂亮”或“Agent 化程度高”。判断顺序固定：

`一行代码能可靠完成 → Code`
`一次普通模型调用（备好上下文、无工具循环）能可靠完成 → Direct AI`
`必须调用工具/Skill 并根据中间结果继续决策 → Agent`
`涉及作品主权、重大创作选择、不可逆或高歧义决定 → 作者`

新增 runtime 必须满足真实 consumer blocker。不得为了统一形式把本来简单的模型请求包装成 Agent 工作流；也不得为了减少 Agent 把真正需要多步骤工具执行的任务压成一次 Prompt。Borrow-first 继续有效：对成熟项目的横向复核只借“普通模型调用与 Agent 工作流并存、检索/数据层可独立于 Agent、Agent 用于工具与多步骤编排”的结论；**不引入这些框架本身**（Dify / LangChain / LangGraph / AutoGen / LlamaIndex 等），Go Write 已有自己的 State、Context、Knowledge 与 Skill 合同，重复引入只增加维护面。

### 15.2 作者编辑与显式状态刷新

作者对正文、细纲、人物、关系、伏笔、故事线、世界/系统等内容的明确编辑，立即由 Code 保存为 authoritative truth；保存作者编辑不自动调用 Direct AI 或 Agent。持久化、revision/hash、字数、章节结构、current/future/retired 标记、图谱投影及其他可由代码确定的视图必须立即更新。

Routine semantic consolidation 只有一个作者触发入口，作者侧概念名称为「更新作品状态」。作者可以无限期继续编辑而不执行该动作。统一流程为：

`作者编辑 / 接受正文 → Code 持久化真相并记录确定性 delta → 作者继续编辑期间零 AI 调用 → 作者显式点击「更新作品状态」 → Code 收集上次确认刷新以来的变更及必要当前项目 Context → Direct AI 执行有界语义整合 → Code 校验结果 → 作者在需要处审核/确认语义后果 → 刷新项目 authority / 派生语义状态 → 刷新 Story Map / Context 投影`

Code 必须记录自上次确认语义刷新以来的变更；常规刷新优先消费变更区域及必要相关当前 Context，不得定义为每次重读全书。全书/深度重分析只能是例外任务。

### 15.3 语义状态未刷新时的上下文权威顺序

下游消费顺序固定为：

1. 最新明确作者内容 / 决定
2. 最新明确由作者维护的结构化记录
3. 最新接受正文
4. 最新确认的派生语义状态
5. 相关的 active future planning
6. 外部知识（仅 advisory）

存在未刷新变更时，StoryPlan、StoryWrite、Review 不得把旧派生状态当成比作者最新编辑更新的事实；Code 应将相关 pending/unconsolidated changes 暴露给任务 Context。写作、规划和审阅可以继续，不得把状态刷新作为强制阻塞；受影响区域以最新源内容/手工数据覆盖过时摘要。

### 15.4 五类职责边界

**Code（确定性事实与唯一账本）**：持久化；project identity；IDs / refs；revision/hash 与 stale 守卫；diff/change tracking；字数、章节与结构事实；current / future / retired 投影；图谱确定性渲染；退役 / 恢复；KnowledgeRetrieve 执行；Context 校验、检索与组装；AI/Agent 结果校验及安全 writeback。凡代码可以 100% 确定的事项，不调用模型。

**Direct AI（仅作者触发的例行语义整合）**：只有在作者显式执行「更新作品状态」且准备好的 Context 足够时，才处理人物当前状态/摘要、关系影响、已发生事件、时间语义、伏笔/开放线索、世界/地点/组织/系统状态影响、章节实际摘要、细纲与正文关系、planning-impact candidate 等有界语义工作。Direct AI 不决定作品创作方向，不覆盖作者控制字段。

**Agent + 既有 Skills/tools（需要工具与多步骤决策的任务）**：NewProject / 故事设计中需要工具或知识决策的工作；多轮 KnowledgeRetrieve 的重大 Foundation 设计；StoryPlan / 重要重规划；StoryWrite；深度 Review；BookDistill / MethodDistill；深度来源研究；以及任何依赖中间结果继续调用工具并作出决策的任务。不能因为普通模型也能生成一段文字，就把需要工具调用、迭代检索、Context 选择或多步创作推理的任务降级为 Direct AI。

**作者（创作主权）**：核心前提；世界硬规则；核心人物身份；重大关系选择；重大系统/故事方向；是否采用歧义/创造性后果；正文/规划/地基的最终 authority。「更新作品状态」只整理既有作者真相的后果，不为作者创造 authority。

### 15.5 Skill ≠ Agent

Skill = 稳定可复用的能力/工作流合同；Agent = 只在需要模型引导的多步骤工具使用时才使用的执行者。两者不绑定。`KnowledgeRetrieve` 与 `ContextCompiler` 在合适处保持代码执行；`SourcePrepare` / `MethodPrepare` 确定性阶段代码执行；`BookDistill` / `MethodDistill` 确定性阶段代码执行、语义阶段 Agent 执行（其价值依赖迭代阅读、证据核验、中间判断与收敛）；`StoryPlan` / `StoryWrite` 保留既有合同，只在真实使用证明某一子任务可安全降级为 Direct AI 时再做最小迁移，不因本节立即重写冻结 Skill。禁止为人物、世界观、关系、伏笔、力量体系再创建独立领域 Skill。

### 15.6 唯一共享项目真相（不可协商不变量）

Author、Code、Direct AI 与 Agent 都读取同一项目 authority 与派生快照：

- Direct AI 不得拥有 AI 人物库；
- Agent 不得拥有 Agent 世界库；
- 页面不得拥有页面本地故事真相；
- 一切 accepted/durable 变更都回到同一条校验 / settlement / writeback 路径。

外部知识保持分离：`02/04 知识 → advisory 输入`；`03 项目 authority → 原创事实真相`。

### 15.7 知识驱动重大基座设计（前瞻合同，未实现）

新书先通过既有 StoryDesign 确定故事方向并创建正式作品；作者明确选择「完善作品地基」后，才扩展现有 FoundationDesign 薄编排。批准的最小流程：`StoryDesign 确定方向 → 作者明确完善作品地基 → FoundationDesign 按题材和当前缺口分解人物/关系/世界/地点/组织/system/故事线/伏笔/悬疑问题 → 按主题有界调用现有 KnowledgeRetrieve（每轮少量 reference_bkp / method_source / validated_knowledge）→ Agent 比较来源、scope、boundary、counterevidence → 综合提案 → 作者选择/编辑 → Code 经既有校验/writeback 写回同一 ProjectModel authority`。

题材不需要的维度可不产生，0 个知识命中仍合法；知识不能压过作者明确意图。不得为此新建 Foundation Skill、Knowledge Router、状态库、图谱 runtime 或第二套基座写入路径。

### 15.8 Direct AI 最小实现原则

只增加一条薄通道：从 Settings 读取作者显式配置的 base_url / model（API Key 只进 OS keyring），一次请求，返回文本/JSON，timeout / error 处理，最小非机密审计。该通道只能由作者显式「更新作品状态」触发 routine semantic consolidation，不能因保存、持续编辑或后台轮询自动触发。Direct AI 结果先由 Code 校验，再按既有作者确认/安全 writeback 合同处理；不得直接覆盖 Canon 或作者控制字段。语义合同校验继续由既有解析器承担，AI runner 不重复 schema 校验。不建：AI 框架、provider registry、workflow graph、middleware pipeline、memory service、prompt registry、session manager、multi-agent 层、vector store、RAG 层、KG、自动模型路由器、成本优化器、AI character/relationship database、独立 state store、队列系统或领域 Skill。

### 15.9 代码模块 ownership

应用代码模块 ownership 以 `07_工作台应用/MODULES.md` 为准（project / ai / agent / creation / knowledge / materials / infra）。logical ownership first，move-on-touch：新代码直接进入正确模块；老文件只在真实修改时顺手迁移；不允许新旧两套实现并存。

### 15.10 开发判定口诀

新增一个功能前只问四个问题：（1）代码能确定吗？能 → Code。（2）一次模型调用能完成吗？能 → Direct AI。（3）必须调用工具/Skill，并根据中间结果继续行动吗？是 → Agent。（4）这是作品主权或重大创作选择吗？是 → 作者确认。已有能力能完成，就不再造新模块、新 Skill、新 Agent runtime。

## 16. 当前里程碑（NEXT）：桌面与作者面产品收敛

「更新作品状态」作者触发的语义刷新已经实现；保存/采用只做 durable Code 写入并记入既有 author-change ledger，项目栏显式动作按 cutoff 做有界 Direct AI 整理，post-cutoff 编辑保持 pending，StoryPlan/StoryWrite/Review 在未刷新时仍可继续。**这一能力现在是本阶段的既有前提，不再是 NEXT 本身。**

当前 NEXT 固定为：

1. **桌面启动 P0**：证明双击正式入口能稳定打开；若失败，建立最小持久诊断后定位真实根因。自动 checker/build/pytest 不得替代作者 GUI 启动验收。
2. **Settings 收敛**：删除重复分区/重复状态/重复“重新检测”；把持久 AI/API、Agent/执行方式、审计诊断和 session-only 偏好按作者任务重新分层。先收 ownership，再调布局。
3. **六页收敛**：按 §8.3-D 对齐产品名称和职责；概览承接重新进入作品的摘要与一个继续动作；Story Map 保持派生但可复用 Foundation 共享编辑器；大纲与规划、正文管理共享稳定连续章号；项目状态确认详情不挤占共用顶栏。
4. **现有能力的最小补齐与真实连续使用**：以既有 FoundationDesign 承接作者明确的「完善作品地基」，并在不新建 Skill/runtime 的前提下补齐题材动态基座、卷/阶段—章节稳定关联、作品简介/核心梗概持久化等前瞻缺口；随后作者连续执行“打开作品 → 编辑/保存 → 规划 → 写作 → 更新作品状态 → 确认语义后果 → 检查 → 继续创作”，只修真实暴露的阻塞或重复负担。
5. **阶段退出后才评估新能力**：没有真实 consumer blocker，不增加大型 runtime、领域 Skill、第二状态系统、通用 AI 编排或额外作者页面。

本轮 UI 工作属于**产品职责收敛**而不是视觉重做；已有 authority / Context / Knowledge / Agent / Direct-AI 合同默认保持冻结，除非上述真实使用直接证明它们存在根因缺陷。

## 20. 长篇创作生命周期不变量（LONGFORM_AUTHORING_LIFECYCLE_CLOSURE，2026-09-02）

以下不变量已实现并被自动化测试证明（检查点 `feb8ed2` / `1e8525a` / `5f4d64b` / `191c92c`）；后续开发不得违反，修改需同步更新本节。

### 20.1 三个时间层（唯一权威心智模型）

- **稳定基座（Foundation / stable truth）**：身份与长期规则；作者字段默认稳定，正文/语义整理不得静默改写。
- **当前故事状态（current state）**：允许随已接受/手工正文演进；批量「更新作品状态」中每条语义后果必须绑定已捕获的源变更（`source_change_ids`），只有真实正文变更在源中才能推进作者拥有的 dynamic 字段；截止点之后的作者编辑永不被本次刷新触碰。
- **未来规划（future plan）**：不是 Canon；版本化、可被取代、允许变化。
- 非正文的语义解释永远不得覆盖作者拥有的动态字段；歧义/创造性后果必须作者确认。

### 20.2 规划血缘与取代（plan lineage + supersession）

- 每个规划派生的未来对象/依赖/章节目标都带 `planning_source_ref`（唯一确认决策）与 `planning_plan_ids`；活动性只由冻结 `resolve_plan_activity` 推导，不存在第二个规划状态库。
- 被取代规划（或其源整体失效）的投影不再是有效未来：确认写回时在同一次 ProjectModel mutation 内退役，读侧快照/上下文/章节目标另有防御性过滤；历史物理保留可审计。
- 同一章号永不多于一个有效活动 `chapter_target`：写入侧强制，替换时确定性退役旧目标；绝不按标题匹配；正式正文绝不被规划替换删除。
- **既有实体的未来走向不是第二个身份**：规划对既有人物/关系/故事线/伏笔/悬疑/体系的未来变化以 `future_trajectory`（附 `target_ref`）表达，不新建同名身份；轨迹不因被规划而成为 current，正文实现后由既有结算路径推进当前真相。
- 作者新编辑触及候选的源/受影响对象或章节时，确定性作废相应影响候选。

### 20.3 作者修改 → 影响 → 显式局部重规划（绝不自动）

- 影响分析只在作者显式「更新作品状态」时由 Direct AI 基于确定性前沿（显式依赖邻居/未来轨迹/故事线/伏笔/章节目标/同阶段后续章/血缘）产生候选；候选的 refs/章号/阶段必须解析到真实项目事实，否则整批拒绝。
- 候选生命周期：pending_author → deferred / in_replan → resolved / obsolete；「暂时保留」只是状态转换，绝不标记旧规划正确、绝不重写任何规划。
- 重规划只由作者显式发起（`planning_mode=impact_replan` + 精确候选 id）；确认原子完成：写入新确认规划决策 + 只退役被替换的规划派生投影 + 保留无关规划 + 解决处理过的候选；失败整体回滚（Story State + ProjectModel + 候选状态）。
- 任何作者编辑/保存/影响分析都不得自动启动 StoryPlan。

### 20.4 分层长篇规划（同一 StoryPlan 操作的结构化模式）

- `planning_mode ∈ free | book | stage | near_term | impact_replan`；模式/范围存于请求元数据并流经同一 finalize/confirm 路径，不新建引擎。
- **规划全书**：故事引擎/阶段/弧光/关系走向/体系推进/故事线/伏笔与粗骨架；远期章节保持粗粒度，绝不一次生成数百章场景级细纲。
- **规划本卷/阶段**：必须绑定真实 `stage_ref`，绝不按标题推断。
- **细化近期章节**：章节范围显式、有界（单次 ≤12 章）、作者可见；绝不静默改写范围外骨架。
- 分层有效优先级：同章最新活动近期细纲 > 章节骨架 > 被取代规划；已接受正文/当前真相永远高于未来规划。
- 知识策略（book/stage）：Agent 可把真实问题分解为 ≤4 个知识需求；每个 need 各自执行一个有界 KnowledgeRetrieve round，每 round 选择 ≤3 条、全请求 unique selected ≤8；每 round 精确绑定 request/project/turn/query/package，全部验证后才形成请求级 bundle；0 检索/0 选择始终合法，finalize 不二次检索，Context 只能消费 bundle 中真实选中的 refs。
- StoryWrite 只消费当前章有效细纲（或骨架）+ 直接参与实体的未来走向 + 一跳显式依赖 + 上一章实际结果/近期正文；绝不注入全书规划。

### 20.5 BookDistill 全书验收门（协议 0.3，不追溯）

- 新蒸馏 BKP 声明可检索前必须完成一次显式全书综合审计（`BKP_ACCEPTANCE_REPORT.md` + `acceptance_data` JSON 块）：重要全书级发现必须成为可追溯 canonical 卡，或显式说明不入卡原因；不设固定卡数/类型维度/文学评分。
- `scripts/acceptance_gate.py` 做确定性机械校验（身份/指纹/卡 id 真实性/卡数一致/无 duplicate/PASS 不与 blocking 缺口共存/retrieval_ready 与状态一致/evidence 溯源）；仅全部通过且 PASS 才写入 `acceptance` 块。
- KnowledgeRetrieve 对 `acceptance.required=true` 的包只在 `status == "PASS"` 时纳入；REVIEW/非法排除；旧版 v0.1/v0.2 无 acceptance 块保持原可检索行为（不迁移）。
