# AI-Write 长期开发手册

> CURRENT_PHASE = REAL_WRITING_USAGE

## 1. 项目定位

AI-Write 是作者主导、AI 辅助的中文长篇小说创作工作台。不是一键自动写整本书，也不是只会服从修改指令的文字工具。

创作流程：`参考/研究 → 构思 → 规划 → 写 → 审阅 → 修改`

理想体验：工作台准备状态与知识 → AI 生成/修改 → 独立诊断 → 作者反馈 → 针对性修订 → 作者接受 → State 结算 → 下一轮。作者不需要理解 Schema、手动挑 Skill、维护状态表。

## 2. 核心原则

### Borrow-first

真实问题 → 查成熟上游 → 最小真实测试 → 能借就借 → 只补剩余缺口。自研集中在：协议、路由、胶水、BKP、中文长篇适配、作者控制。

### 案例只暴露问题，不决定架构

单个章节或漏检不能直接升级成长期 Schema / Skill。回到完整能力地图和成熟上游判断系统性缺口。

### CAPABILITY_FIRST_CONSUMER_DRIVEN

最终作者可感知工作台能力优先于单个子系统完善度。子系统达到最小合同并经过真实验证后默认冻结；后续缺口由真实下游消费者暴露。

开发决策规则：只有同时满足（1）真实正文/真实使用暴露问题；（2）问题重复或严重；（3）现有能力不能低成本解决；（4）新代码能明显降低长期负担，才允许新 runtime。否则 DO_NOT_BUILD。

窄口径更新：`THIN_ORCHESTRATION_BUILD_ALLOWED`——只允许复用现有合同的薄操作层（消除已两轮重复出现的机械摇柄）；不代表 Writer platform 获批；不允许新 Final Schema；不允许重开 StoryPlan / Context Compiler / BookDistill / KnowledgeRetrieve。

### 参考知识与原创事实必须隔离

- BKP：参考作品中提炼出的写作知识、模式、观察和边界
- Canon / Story State：我们自己正在创作的小说中已确定/已发生的事实与状态

自己的小说事实和作者要求始终高于参考作品建议。参考书只能提供方法和启发，不能污染或覆盖原创作品 Canon。

### KNOWLEDGE_SHARED_AUTHORITY_ISOLATED

多部原创小说可以共享 `02_素材知识库` 与未来成熟的 `04_写作知识库`；但每部小说的 project_id、Author Intent、Story State、approved_plan、Decision、正式正文和项目专属资料必须完全隔离。

切换作品等于切换整套原创 project context；共享知识不等于共享原创 authority。

### 作者控制 ≠ 作者审批

重要创作方向由作者控制；机械工作后台自动完成。只有真正存在创作歧义、冲突或高风险不可逆操作时才需要作者确认。

### 基础模型创作能力优先

外部知识、BKP 和专业能力默认按需、稀疏、问题驱动地介入。0 个知识命中/采用是合法结果。

### 自由规划优先与 BKP 后置

E2-B 验证：强模型自由规划优先原则成立；BKP 后置策略得到支持。

## 4. 根目录长期职责（ROOT_LAYOUT_FINALIZATION）

`ROOT_LAYOUT_FINALIZATION = COMPLETE`

当前根目录职责冻结为：

| 目录 | 唯一职责 | 作者使用方式 |
|---|---|---|
| `00_项目控制` | 工作台系统状态、长期原则与开发手册 | 系统后台；作者通常不操作 |
| `01_原始素材` | 外部原始来源 + canonical material registry | 作者投放/管理外部素材 |
| `02_素材知识库` | 与具体外部素材绑定、可追溯来源的长期知识 | 后台维护；作者按需查看 |
| `03_作品工程` | 原创小说的设定、规划、正文与 production Story State | **作者日常创作核心目录** |
| `04_写作知识库` | 经跨作品与真实创作验证的长期可复用写作知识 | 当前非日常操作目录 |
| `05_Skills与自动化` | 工作台正式能力实现 | 系统后台；作者通常不操作 |
| `06_工作区` | 可删除、可重建的临时运行空间 | 系统后台；作者通常不操作 |

作者日常主要操作 `01_原始素材` 与 `03_作品工程`；`02_素材知识库` 按需查看；`04_写作知识库` 当前不要求作者管理；`00/05/06` 属后台层。

根目录编号表示资产/职责分层，不表示 runtime 执行顺序。例如参考知识链真实运行可为 `01 → 06 → 02`，不因此调整编号。

除非真实使用暴露重复职责或长期操作负担，否则不再重命名、重新编号或合并一级目录。

## 5. StoryPlan 长期冻结原则

1. 不使用固定 book/volume/arc/chapter/scene 层级
2. approved_plan 保留 append-only history
3. 当前有效 planning 是 derived view
4. 局部重规划通过显式 supersedes 表达
5. planning 永远不等于 Canon
6. stale Brief 必须重新编译
7. TEST_ONLY simulation authority 永远不等于作者真实确认
8. StoryPlan 当前停止扩展

## 6. Context Compiler 长期冻结原则

1. 不默认注入整个 Story State
2. State selection 必须 explicit；空 selection 不得 fallback 全量
3. selected_story_state 与 selected_bkp_hits 永远分区
4. Context Package 是可重建派生层，不是 authority
5. 当前不做：最终 Context Schema、token budget optimizer、embeddings、vector DB

## 7. REAL_PROJECT_WIRING 长期合同

`REAL_PROJECT_WIRING_DESIGN = FROZEN`

当前最大未验证缺口不是新的文学能力，而是把已经冻结/可用的 StoryDesign、StoryPlan、ContextCompiler、StoryWrite 接到真实 `03_作品工程/<作品>/`。

### 7.1 作者输入合同

作者使用自然语言，不要求知道内部 Skill 名称，也不要求维护固定的 StoryDesign/StoryPlan/Context/KnowledgeRetrieve Prompt 模板。

常见表达可以是：

- `新建《作品名》。我现在的想法是……`
- `继续《作品名》。今天我想……`
- `切到《作品名》……`
- `基于已经确定的方向，规划……`
- `写下一章/下一场，我希望……`
- `这部分不要……改成……`
- `这个方向确定，就按这个走`
- `这版接受，定稿`

前六类属于自然任务描述；后两类涉及长期 authority，必须语义明确。类似“还行”“先这样看看”“差不多”不得自动升级为确认或 acceptance，不确定时只做一次最小澄清。

### 7.2 每部作品的私有边界

每部真实作品直接位于：

```text
03_作品工程/<作品名>/
├─ README.md
├─ 01_设定与人物/
├─ 02_规划/
├─ 03_正文/
├─ 04_资料与灵感/
└─ _工作台状态/
```

`_工作台状态/` 绑定现有 frozen runtime 的 `project_dir`，保存 Author Intent、Story State、Decision/authority 等 production state；Context、recent prose、临时 Brief 等仍是可重建派生物，不要求长期保存。

任何会修改正式正文、Story State、planning、Decision 的动作，都必须先唯一解析当前作品与 `project_id`。多作品存在而用户只说“继续写”时不得猜；用户明确说作品名时直接切换。

### 7.3 正文存储：章存储，scene/write-turn 运行

正式正文物理存储按章：

```text
03_正文/
├─ 第001章.md
├─ 第002章.md
└─ ...
```

只有作者明确接受的版本才进入 `03_正文`。

StoryWrite 运行和 production acceptance 继续使用稳定 `scene_ref` / write-turn ref。一个章节可以包含多个 accepted ref；如果用户一次写完整一章，也允许一个较大的 accepted unit。不得把 scene 变成强制文学层级。

REAL_PROJECT_WIRING 只需维护最小 accepted ref → 正文章节映射，使 `accepted_text:<scene_ref>` 可以追溯到实际正式正文。不要升级成数据库、正文知识图谱或复杂事件系统。

### 7.4 长篇上下文分层

每次写作不重新阅读全部正文。继续使用现有已验证结构：

1. Story State：长期连续性与 Canon 状态；
2. active approved_plan：未来方向；
3. ContextCompiler：只选择当前任务需要的少量 State；
4. recent prose：最近 accepted 正文末尾约 1000–2000 字，解决短距离文字连续性；
5. 旧正文：真实需要回溯具体原文时才定向读取对应章节；
6. BKP：明确 knowledge need 时少量调用；0 BKP 是正常路径。

当前禁止因为“将来可能有用”而提前建设原创正文全文 RAG、embedding、vector DB。若百万字级真实创作反复证明定向旧文查找成为稳定瓶颈，再由 consumer evidence 决定是否升级。

### 7.5 多作品与共享知识

多本小说同时更新时：

- 每本书有独立 project_id / State / Planning /正文 / Decision；
- 切换作品必须重建该作品的当前 Context，上一作品 Context 不得继续沿用；
- 作品专属调查/灵感放 `03_作品工程/<作品>/04_资料与灵感/`；
- `02_素材知识库` 跨项目共享；未来 `04_写作知识库` 也可跨项目共享；
- BKP 永远只是参考知识，不因被某作品使用过而获得另一作品的 Canon authority。

### 7.6 正文 acceptance 生产链

冻结目标链：

`候选正文 → 作者明确接受 → 写入/更新对应章节 Markdown → 登记 accepted scene ref → mechanical settlement → 写回当前项目 production Story State → 下一轮从新 State + recent prose 继续`

未接受草稿不得进入正式正文；未接受正文不得触发 production settlement。`ambiguous` / `creative` settlement 候选仍不得写入 Story State。

### 7.7 实现范围

`REAL_PROJECT_WIRING_IMPLEMENTATION = NEXT`

只允许增加最薄的项目操作/接线层，完成：

1. 新建/打开/解析真实作品工程；
2. 初始化 `_工作台状态` 并绑定现有 frozen runtime；
3. 保存 accepted 正文与最小 accepted-ref 索引；
4. 复用现有 StoryWrite production settlement 并把 `new_state` 安全持久化到正确作品；
5. 项目切换与多项目隔离；
6. 验证共享 `02_素材知识库` 仍可被不同项目按需调用。

不得重开 StoryDesign / StoryPlan / ContextCompiler / StoryWrite 的既有文学/authority 语义；不得新增 Final Schema；不得建设完整 Writer platform；不得增加原创全文 RAG。

## 8. Git 与文档纪律

无明确授权禁止：`reset / restore / clean / force push / rebase / merge`。

临时 worktree 默认进入系统 TEMP，不在 E:\ 根留下 AI-Write-*。任务完成后删除 worktree。

长期文档只留稳定原则和当前路线；具体过程放工作区和 Git 历史。
