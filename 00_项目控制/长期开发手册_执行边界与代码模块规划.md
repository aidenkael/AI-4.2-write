# Go Write 长期开发手册正式附录：执行边界与代码模块规划

> 日期：2026-08-31  
> 状态：APPROVED_DESIGN  
> 作用：本文件是 `长期开发手册.md` 的正式补充。凡历史章节中“所有 AI 任务都由 Agent 承载”的表述与本附录冲突，以本附录为准；现有运行时在迁移完成前仍按当前代码工作，不把设计目标冒充已实现。

## 1. 根原则：最小实现，效果优先

Go Write 不追求“架构漂亮”或“Agent 化程度高”。判断顺序固定为：

`一行代码能可靠完成 → 代码`  
`一次普通模型调用能可靠完成 → Direct AI`  
`必须调用工具/Skill并根据中间结果继续决策 → Agent`  
`涉及作品主权、重大创作选择、不可逆或高歧义决定 → 作者`

新增 runtime 必须满足真实 consumer blocker。不得为了统一形式，把本来简单的模型请求包装成 Agent 工作流；也不得为了减少 Agent 而把真正需要多步骤工具执行的任务压成一次 Prompt。

Borrow-first 继续有效。2026-08-31 横向复核只参考高星成熟项目：Dify（约15.4万星）、LangChain（约14.5万星）、AutoGen（约6.1万星）、LlamaIndex（约5.2万星）、Vercel AI SDK（约2.65万星）。借鉴结论仅限：普通模型调用与 Agent 工作流应并存、检索/数据层可独立于 Agent、Agent 用于工具与多步骤编排。**不引入这些框架本身**；Go Write 已有自己的 State、Context、Knowledge 与 Skill 合同，重复引入只增加维护面。

## 2. 五类职责最终边界

### 2.1 作者：创作主权

作者必须负责：
- 作品核心方向、题材、主题、读者承诺；
- 世界观硬规则、主角核心人设、重大关系、关键体系与重大剧情选择；
- 多个合理方案之间的取舍；
- 是否接受 AI/Agent 规划、正文、重大语义推断；
- 明知与既有设定冲突但有意覆盖时的最终决定；
- 是否对外部资料执行提纯/蒸馏等重大知识生产动作。

AI/Agent 可以提出方案和影响分析，但不得替作者决定“作品最终应该变成什么”。

### 2.2 Code：确定性事实与唯一账本

代码负责：
- project_id、对象 ref/ID、版本、hash、原子写、回滚；
- 文件保存、章节、字数、顺序、current/future/retired 状态；
- 明确依赖关系、图谱投影、明确时间后的日期/时长计算；
- delta/diff、stale guard、项目隔离、权限/authority 校验；
- ContextCompiler 的确定性编译与验证；
- KnowledgeRetrieve 的确定性检索；
- AI/Agent 输出 JSON/schema 校验；
- 统一 writeback/settlement 门；
- 任务状态、去重、取消、失败与重试的机械部分。

凡代码可以 100% 确定的事项，不调用模型。

### 2.3 Direct AI：高频单轮语义工作

Direct AI 的判定标准：给定精确 Context，一次或极少数固定模型调用即可返回结构化结果，不需要模型自行决定下一步调用什么工具。

优先迁入 Direct AI：
- 人物一句话介绍、人设、背景、语言/行为锚点摘要；
- 正文变化后的角色状态、关系变化、事件、相对时间、伏笔、世界/地点/组织状态提取；
- chapter_actual_result；
- 正文与细纲偏差、planning impact candidate；
- 局部一致性诊断；
- 已给定检索结果后的知识应用；
- 不需要工具循环的普通创作/改写/局部规划。

Direct AI 输出仍只是 patch/candidate；真正写回统一作品状态必须经过 Code 的合同校验。

### 2.4 Agent：需要行动与多步骤决策的任务

Agent 只在以下情况有明确价值：
- 模型需要调用一个或多个 Skill/工具；
- 根据第一次工具结果决定下一步查什么、读什么、再调用什么；
- 需要跨多文件、多来源、跨尺度持续工作；
- 任务本身是长流程研究/蒸馏，而非一次结构化推理。

明确保留给 Agent：
- BookDistill 的语义 Discovery / Deep Dive / 总编辑式收敛；
- MethodDistill 的语义抽取阶段；
- 新书创建或重大重构时的“作品基座研究与设计”；
- 阶段/卷结束、重大重写后的全书级定向重校准；
- 需要反复 KnowledgeRetrieve、读原文/文件、比较多个来源后再决策的深度研究任务。

Agent 对话历史不是项目记忆，也不是 authority。

### 2.5 Skill：稳定能力，不等于 Agent

Skill 是经过验证的稳定能力合同；Agent 是可能调用这些能力的执行者。两者不绑定。

- `KnowledgeRetrieve`：代码可直接调用；不需要为了“调用 Skill”而启动 Agent。
- `ContextCompiler`：代码执行；AI/Agent只负责提供语义 selection。
- `SourcePrepare` / `MethodPrepare`：确定性阶段由代码执行。
- `BookDistill` / `MethodDistill`：确定性阶段代码执行，语义阶段 Agent 执行。
- `StoryPlan` / `StoryWrite`：保留既有合同；未来只在真实使用证明某一子任务可安全降级为 Direct AI 时再做最小迁移，不因本附录立即重写冻结 Skill。

禁止为人物、世界观、关系、伏笔、力量体系再创建独立领域 Skill。

## 3. 新书创建之初：重大基座必须使用蒸馏知识，但不做巨大工作流

一本新书在确立世界观、人物、关系、体系、主冲突、故事线等重大基座时，不能只靠裸模型生成；也不能把整个知识库塞进 Prompt。

批准的最小流程：

`作者初始想法`
→ `Agent 分解 5~8 个真正需要研究的 knowledge_needs`
→ `按问题多轮调用现有 KnowledgeRetrieve`
→ `每轮只取少量高价值 reference_bkp / method_source / validated_knowledge`
→ `Agent 比较来源、scope、boundary、counterevidence`
→ `综合形成少量可选基座方案`
→ `作者确认/修改`
→ `Code 按统一 authority 合同写入 Story Bible / planning`

重点：
- Agent 的价值在“根据中间检索结果决定下一步”，不是比普通模型更聪明；
- 不要求每次固定跑满 5~8 个问题，按实际复杂度缩减；
- 0 个知识命中仍合法；知识不能压过作者明确意图；
- 不把“世界观设计”再造一个新 Skill；继续复用 StoryPlan/KnowledgeRetrieve/现有领域合同；
- 当前 KnowledgeRetrieve 的单次 top-N/少量卡机制适合局部任务；重大基座任务通过**分问题多轮调用**解决，不急于引入向量库/KG。

## 4. 现有蒸馏底座判断

当前 BookDistill 已具备逐章 evidence-first、多视角 Discovery、跨章聚合、scope/boundary/confidence/counterevidence、人物/关系/Reader Promise/结构/信息/读者体验/微观 craft 等能力；MethodDistill 能产出 principle / diagnostic / procedure / checklist / failure_mode，并带 conditions、steps、checks、failure_modes、use_stages、problem_types、tags。

结论：**蒸馏知识结构目前足以支持新书人物、世界观、关系、体系、结构与正文创作，不重做蒸馏 Skill。** 当前更值得验证的是检索质量与重大基座任务的多轮调用效果。

## 5. 唯一作品体系：Code / AI / Agent 绝不各自为政

所有创作参与者读取并维护同一逻辑作品状态：

`Author Intent + Story Bible/Project Model + production Story State + active Planning + Chapter Files + Chapter Actual Results`

统一由 `Project Snapshot` 提供当前有效视图。

规则：
- 作者编辑同一套源数据；
- Code 维护同一套 authority、版本和文件；
- Direct AI 只读相关 Context并返回结构化 patch/candidate；
- Agent 也读取同一 Snapshot/Context/Knowledge，不建立自己的人物库、世界观库或长期记忆；
- AI/Agent 的任何写入都必须回到统一 author_edit / settlement / confirm/writeback 门；
- Story Map、Overview、Review、摘要、Context 都是派生层，不拥有第二份事实；
- 外部知识库是唯一合理的独立知识域，但永远是 advisory，不能自动进入原创 Canon。

## 6. 未来 Direct AI 最小实现原则

若开始接入独立模型 API，只允许先增加一条薄通道，不建设新平台：

```text
ai_runner.run_structured(task, context, schema, model_profile) -> structured result
```

最小职责：
- 从 Settings 读取作者明确配置的 AI provider/model；
- 一次请求；
- JSON/structured output；
- timeout/cancel/error；
- 最小非机密审计；
- 不直接写 Canon。

第一候选迁移对象：`change_settlement` 中高频人物/关系/事件/世界状态/章节实际摘要等轻语义工作。

暂不建设：
- LangChain/LangGraph/Dify/LlamaIndex runtime；
- 第二套 workflow engine；
- session/memory framework；
- multi-agent framework；
- event bus；
- 新数据库；
- vector DB / KG / 全文 RAG；
- 自动模型路由器；
-复杂成本优化器。

## 7. 当前代码模块化原则

代码已经较多，但当前不批准“大搬家式重构”。采用 **logical ownership first, move-on-touch**：

1. 先冻结模块职责与依赖方向；
2. 新代码直接进入正确模块；
3. 老文件只有在真实修改时顺手迁移；
4. 不为了目录漂亮一次搬几十个文件；
5. 每次迁移必须保持 public contract 和测试不变。

详细物理/逻辑模块见 `07_工作台应用/MODULES.md`。

## 8. 开发判定口诀

以后新增一个功能前只问四个问题：

1. **代码能确定吗？** 能 → Code。
2. **一次模型调用能完成吗？** 能 → Direct AI。
3. **必须调用工具/Skill，并根据中间结果继续行动吗？** 是 → Agent。
4. **这是作品主权或重大创作选择吗？** 是 → 作者确认。

如果以上已有能力能完成，就不再造新模块、新 Skill、新 Agent runtime。
