## 2. 为什么建立 G4

G3 证明了跨书 Retrieval，但没有证明：

1. 多书智慧能结合当前原创情境形成真正可用的方向；
2. AI 能辅助规划/修改，同时作者仍掌握重大创作取舍，并可靠维护长篇状态。

因此 G4 先做“神经中枢”，不先做完整 Writer。

## 3. 唯一目标

把：

`Author Intent + Story State + Current Focus + Reader Goal + 少量 BKP Hit`

编译成小而相关的 Context，再支持创作方案/修改，并形成可靠状态闭环。

G4 的产品约束：

> **作者主要看正文、说感觉、做重大取舍；后台自动选择技能、调用知识、修改文本、检查连续性和维护机械状态。**

## 4. 作者控制边界

**作者控制 ≠ 作者审批。**

- 重大创作变化：作者显式确认；
- 已接受正文中的明确事实：系统自动机械结算；
- 歧义/推断：暂存候选或询问作者；
- BKP / AI 推演 / Context：不得直接写入 Canon。

正文接受本身可以作为其中明确事实的 authority，不需要作者逐条审批状态字段。

1. Author Intent；
2. Story State / Canon；
3. Creation Brief；
4. Context Package；

## 8. G4 退出条件

G4 closeout 前必须证明：

- 权威状态可文件化恢复；
- BKP / Canon 严格分离；
- Context 小而相关、有来源、可重建；
- 不同创作问题能做情境化 Synthesis；
- AI 给出的方案/修改有真实差异和边界；
- 作者能用自然语言接受、修改、拒绝；
- 重大创作决定保留作者控制；
- 已接受正文的明确事实能自动结算；
- 歧义/推断不偷渡进 Canon；
- 新会话能靠权威工件恢复状态；
- 无真实阻塞不升级 Retrieval/RAG/KG；
- 作者明确验收后退出。

## 9. 明确不做

当前 G4 不做完整 Writer、完整 Reader/Critic/Editor、正式长篇、UI、大型数据库/KG/向量库、多 Agent 平台，也不为了工程完整度升级 Retrieval。

## 10. 一句话边界

> **G4 的目的不是让作者管理一个复杂系统，而是让复杂后台逐步变得不可见：作者通过正文和自然语言创作，系统负责把知识、技能和状态维护连接起来。**
