# AI-write 项目说明（目录结构与工作流）

> 本文件是当前目录结构的**权威说明**。任何顶层目录调整都必须先更新本文件，并经明确授权。  
> 最近校准：2026-08-12（G3 closeout 后）。

## 一、最终目标

本项目不是资料管理系统，也不以囤积小说全文作为“训练数据”。

目标是：**用 AI 长期辅助真实作者完成不同题材、不同风格的长篇小说创作，并逐步形成稳定、可成长的创作工作台。**

当前重点是 AI 辅助创作，不是模型训练工程，也不是独立 UI 工程。

作者层尽量只面对：

`参考 / 研究 → 构思 → 规划 → 写 → 审阅 → 修改`

后台负责 Book Knowledge、Canon / Story State、Retrieval、Context Compiler、Planner、Writer、Reader / Critic / Editor、Continuity、State Writeback、Controller 等。

## 二、八个顶层目录

- `00_项目控制`：项目级长期控制文件：当前索引、门禁、项目记忆、能力地图、上游路由、阶段 closeout 记录等。
- `01_原始素材`：未加工的原始资料（第三方网络小说、中文文学、外国文学、历史/古代资料、现代专业资料等）。**Local Only，不进入 GitHub。**
- `02_原著蒸馏`：每一部具体参考作品形成的长期知识资产。当前以 **BookDistill + BKP（Book Knowledge Package）** 为核心；保存作品级 Observation / Inference / Work-specific Pattern、Evidence、Boundary、BookProfile 等，不等于跨作品写作定律。
- `03_作品工程`：我们自己正在创作的作品：设定、Canon、人物、关系、大纲、章节、正文、状态等。**最终创作发生的位置。**
- `04_写作知识库`：经过跨作品支持与真实创作验证、确实可复用的高成熟度写作知识。**不是每本 BKP 的必经中转站。**
- `05_Skills与自动化`：已形成实际可调用能力的 Skill / Agent / 脚本 / 自动化 / 运行时组件。
- `06_工作区`：当前进行中的调研、Benchmark、实验、Controller 工作文件、中间分析、临时报告和 Local Only 运行产物。不作为长期知识权威库。
- `99_归档`：已结束、失效、被替代但仍值得追溯的历史资料；长期权威文件大幅收束前，可先原样归档旧版。

未经明确授权，不得新增顶层目录，不得恢复旧目录体系。

## 三、资料与知识生命周期

### 3.1 参考作品进入 BKP

```text
01_原始素材（Local Only）
        ↓
06_工作区 / SourcePrepare（中间处理）
        ↓
02_原著蒸馏 / BookDistill
        ↓
一个作品一个 BKP
        ↓
KnowledgeRetrieve 按创作问题召回少量相关知识
        ↓
03_作品工程中的真实创作
```

正常写作阶段不因为当前场景需要某技巧就重新蒸馏整本原著。

### 3.2 跨作品知识成熟度

单书知识不会自动进入 `04_写作知识库`。

正式知识成熟度：

```text
Source Evidence
→ Observation / Inference
→ Work-specific Pattern
→ Cross-book Pattern
→ Creation-tested Heuristic
→ Production Rule
```

只有经过足够跨作品支持和真实创作验证、确实值得长期复用的高成熟度知识，才考虑进入 `04_写作知识库`。

### 3.3 原创作品自己的状态

`03_作品工程` 中的 Canon / Story State 与参考作品 BKP 必须严格分离。

参考书的 Pattern 不能变成自己作品里“已经发生的事实”；自己作品的人物、关系、时间线、伏笔也不能写回参考书 BKP。

## 四、Local Only 原则

第三方网络小说、世界文学等原始全文**默认只允许保存在本地**。`01_原始素材` 下的原始格式（epub / txt / zip / pdf / azw3 / mobi）由 `.gitignore` 等规则保护，不上传 GitHub。

这些资料用于个人研究，不是可公开再分发的素材。

## 五、GitHub 保存什么 / 不保存什么

**保存：**

- 目录结构；
- README / 项目控制文档；
- 我们自己的分析、BKP 知识层、报告；
- Skill / 脚本 / 自动化；
- 自己创作的作品文本和结构化状态；
- 合规的 provenance / 来源记录。

**不保存：**

- `01_原始素材` 下的第三方原始全文格式；
- `.env` / 密钥 / credentials；
- 大型二进制工具；
- 缓存、临时日志；
- 明确标记 Local Only 的中间材料。

## 六、原始资料保护

`01_原始素材` 中的原始文件**不得覆盖、修改、误删、全量解压或批量格式转换**。

它们以本地文件为准；项目通过 SourcePrepare / metadata / SHA256 等方式建立可追溯输入，不改动原始本体。

## 七、不同类型作品主要研究什么

**网络小说**常重点研究：

- 阅读驱动力；
- 期待与兑现；
- 爽点 / 悬念；
- 节奏与张弛；
- 连载结构；
- 长篇留存；
- 商业叙事能力。

**优秀文学作品**常重点研究：

- 人性与人物复杂性；
- 关系与情感；
- 主题；
- 语言与声音；
- 意象；
- 叙事距离；
- 结构；
- 文学表达。

这不是固定 taxonomy。任何作品都可能在其他维度非常优秀；永久允许：**“重要，但目前无法命名。”**

网络小说与世界文学不存在简单“高低级”关系，目标是吸收各自真正有效的创作智慧。

## 八、“原著蒸馏” vs “写作知识库”

### `02_原著蒸馏`

回答：

> “这部具体作品做了什么？为什么可能有效？证据在哪里？适用边界是什么？”

它依附于作品本身，允许保留：

- BookProfile；
- 作品地图；
- Observation；
- Inference；
- Work-specific Pattern；
- Deep Dive；
- Evidence；
- Scope / Boundary / Counterevidence / Confidence。

### `04_写作知识库`

回答：

> “经过跨作品和真实创作验证后，有没有少量经验值得作为更高成熟度的长期写作知识？”

因此：

**单本作品知识留在 BKP；跨作品重复也不能自动升级成 Production Rule。**

## 九、当前原著 Discovery 原则

BookDistill 不再被要求单枪匹马发现一本书全部精华。

当前方法：

```text
原著（最高事实源）
│
├─ 长篇运行 / 读者动力镜头
│  └─ 优先借 oh-story + AI-Novel-Writing-Assistant
│
├─ Reader / Page Craft 镜头
│  └─ 优先借 creative-writing-skills
│
├─ 必要时 Developmental Deep Dive
│  └─ 优先借 Apodictic
│
└─ BookDistill 总编辑
   └─ 回源核证 → 整合 → 去重 → 组合效果 → 边界 / 反例 / 置信度 → BKP
```

关键纪律：

- 重要观察能力可以直接读取原著，不能只吃上一层摘要；
- BookProfile 是导航 / 预算工具，不是过滤器；
- 允许跨句、跨场景、跨章节组合 Evidence；
- Discovery 可以宽，最终 BKP 必须克制；
- 不因为单个案例新增硬编码规则；
- 不因为分类表没有位置就丢掉重要发现。

## 十、作品工程是最终服务对象

`03_作品工程` 是最终创作发生的位置。

前面所有素材、蒸馏、知识、上游研究、Skill 和技术架构都服务于：

> **帮助作者更稳定地做出好的创作决定，并写出真正愿意继续看的长篇小说。**

不能把“知识多”“报告完整”“Benchmark 严格”“功能数量多”当成项目终点。

## 十一、工作台建设原则

### Borrow-first

AI-write 不从 GitHub 项目中选一个“总冠军”，也不把多个项目粗暴拼接。

正确做法：

- 按真实能力需求看成熟上游；
- 尽量理解其完整工作逻辑；
- 可以直接借、适配后借、只借方法；
- 用薄接口组合；
- 只有真实剩余缺口才自研。

当前核心长期参照包括：

- AI-Novel-Writing-Assistant；
- oh-story；
- creative-writing-skills；
- Apodictic；
- InkOS；
- NovelForge；
- graphify-novel；
- ani-book-skill。

详细路由见 `GitHub候选池_能力路由_v0.2.md`。

### 真实任务优先

普通能力默认：

`快速筛选 → 最小真实任务 → 必要时作者快速判断 → 吸收 / 保留 / 放弃`

只有高价值、证据矛盾、错误固化代价高时才升级严格 Benchmark。

### 作者控制

作者负责重大创作决定。

AI 应：

`给方案 / Evidence / 风险 / 推演 → 作者确认 → 更新计划 / Canon / Story State`

而不是为了自动化最大化替作者决定作品方向。

### 统一的是作者体验与接口，不是强迫所有上游重写成同一种内部实现

可以保留成熟能力原有工作逻辑，通过薄适配层组合。

避免为了“AI-write 看起来统一”而重新造一套功能相同但更差的轮子。

## 十二、文件生命周期规则

这些规则可随项目演进由用户 / Controller 维护，不永久冻结。

### `00_项目控制`

只存：

- 项目级长期规则；
- 当前工作索引；
- 门禁；
- 项目推进记忆；
- 全局能力地图；
- GitHub 上游路由；
- 阶段 closeout 记录；
- 权威且持续更新的项目级索引。

默认不存单轮 Runner、一次性 Agent 指令、临时反馈等。

### `06_工作区`

当前调研、Benchmark、实验、中间分析、临时报告、Local Only 运行产物。

结束后：

- 长期规则 / 决策提升到 `00_项目控制`；
- 单书正式知识进入 `02_原著蒸馏`；
- 真正高成熟度跨作品知识才进入 `04_写作知识库`；
- 历史过程按需进入 `99_归档`。

### `05_Skills与自动化`

只存已形成实际可调用能力的 Skill / Agent / 脚本 / 自动化 / 运行时组件。

### `99_归档`

存放结束、失效、被替代但仍值得追溯的历史资料。
