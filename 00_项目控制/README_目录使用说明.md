# AI-Wirte 项目说明（目录结构与工作流）

> 本文件是当前目录结构的**权威说明**。任何顶层目录调整都必须先更新本文件，并经明确授权。

## 一、最终目标

本项目不是一个资料管理系统，也不以囤积小说全文作为“训练数据”。

目标是：**用 AI 辅助真实作者完成创作流程，逐步形成一个能产出高质量长篇网络小说的创作系统。**

当前重点是 AI 辅助创作，不是模型训练工程。

## 二、八个顶层目录

- `00_项目控制`：项目说明、规则、索引、迁移与整理报告、资产清单等控制类文档。
- `01_原始素材`：未加工的原始资料（第三方网络小说、世界文学、历史/古代资料、现代专业资料等）。**Local Only，不进入 GitHub。**
- `02_原著蒸馏`：以单部作品为完整研究对象的逆向工程结果，以及后续跨书综合结果。
- `03_作品工程`：我们自己正在创作的作品（设定、大纲、人物、章节、正文）。**最终创作发生的位置。**
- `04_写作知识库`：从多部作品与其他资料中沉淀的跨作品、可复用写作知识、方法、案例和规律。
- `05_Skills与自动化`：Agent / Skill / 脚本 / 自动化能力。
- `06_工作区`：格式转换、处理中间态、复核、返工、临时输出。**Local Only，不作为长期知识库。**
- `99_归档`：失效但需要保留的项目资料。

未经明确授权，不得新增顶层目录，不得恢复旧目录体系。

## 三、资料生命周期

```text
01_原始素材
    ↓
SourcePrepare / 06_工作区
    ↓
BookDistill / 02_原著蒸馏
    ↓
跨书综合 / 04_写作知识库
    ↓
StoryDesign / 03_作品工程
    ↓
正文创作与复盘
```

各环节可以并行推进，但数据职责不得混淆。

## 四、Local Only 原则

第三方原著全文默认只允许保存在本地。

包括两层：

1. `01_原始素材` 中 EPUB / TXT / PDF / ZIP / AZW3 / MOBI 等原始文件；
2. `06_工作区` 中由第三方原著生成的完整 Markdown、章节拆分文件和其他处理中间副本。

两者都不得进入 GitHub。

这些资料用于研究，不是可公开再分发的素材。

## 五、GitHub 保存什么 / 不保存什么

**保存：**

- 目录结构与 README；
- 项目控制文档；
- 我们自己的分析、蒸馏结论与报告；
- Skill、脚本、Schema、测试；
- 自己创作的设定、大纲和正文。

**不保存：**

- 第三方原著全文及其格式转换副本；
- `.env`、密钥、credentials；
- 大型二进制工具（如 pandoc.exe）；
- 缓存和临时日志。

## 六、原始资料保护与格式转换

`01_原始素材` 中的原始文件不得覆盖、修改、误删或就地转换。

允许 `SourcePrepare`：

- 只读检查原始 EPUB / TXT / PDF；
- 在临时目录读取或解包必要结构；
- 在 `06_工作区` 生成 Markdown 工作副本；
- 使用 SHA256、章节数量、正文长度等进行来源校验。

禁止任何 Skill 在 `01_原始素材` 内直接改写正文、覆盖文件或因“已有其他格式”而删除备用来源。

## 七、网络小说与世界文学的关系

网络小说与世界文学不存在简单的高低级关系，也不采用两套互相割裂的价值标准。

所有优秀作品首先使用统一核心维度研究：

- 全书结构；
- 剧情推进与节奏；
- 主角、配角与群像；
- 人物关系；
- 场景与对白；
- 情绪与期待；
- 悬念、伏笔与信息控制；
- 世界构建；
- 语言与叙事；
- 主题表达；
- 成功与失败原因。

在统一分析基础上，再根据作品客观形态增加专项研究。例如网络连载作品额外研究章节钩子、连载节奏、长期追读和阶段兑现；某部世界文学如果强情节、悬疑或节奏出色，同样完整提取这些能力。

原则是：**按作品实际优势学习，而不是按“网文/名著”预先决定它只值得学习什么。**

## 八、“原著蒸馏” vs “写作知识库”

- `02_原著蒸馏`：从**某一部具体作品**还原出的完整写作模型，依附于该作品及其证据。
- `04_写作知识库`：经过多部作品比较后形成的**跨作品、可复用**写作知识、方法和规律。

前者强调保留整书上下文，后者强调抽象与复用。

## 九、作品工程是中心

`03_作品工程` 是最终创作发生的位置。设定、大纲、人物、章节、正文和创作复盘都服务于同一部作品。

原著蒸馏和写作知识库只是辅助系统，不允许为了“知识管理完整”而拖延真正创作。

## 十、目录冻结原则

本 README 是当前目录结构的权威说明。

后续新增功能优先通过 Skill、Schema、脚本或现有目录内部扩展实现，原则上不新增顶层目录。

## 十一、合集容器与「来源容器」列

`01_原始素材` 下的“合集/套装”原著（单作者作品合集、多位作者套装）在物理上只占一个目录，
但包含多部**逻辑作品**。处理规则：

- 用脚本按 EPUB 自身 OPF / spine / NCX 结构拆成多本**独立可运行的 EPUB**，拆分基准是文件结构，
  **不是** LLM 猜测章节；原合集永久保留、不修改、不删除。
- 合集目录内放 `collection_manifest.json`（Local Only），登记每本拆分作品的 `book_id`、
  文件名、SHA256、来源容器名。
- 中央索引 `原始素材清单.csv` 用**「来源容器」列**记录“该文件来自哪个合集”，空值表示独立来源。
- **作品身份以 `book_XXXX` + 中央索引为准，不以文件夹名决定**：同一作品若同时有旧目录单本与
  合集拆分本，靠 `book_id` 归并，SourcePrepare 跨目录识别并交叉校验全部候选来源。
- 一个合集在物理目录层面只占一个目录名额，不占用每部作品一个目录。

## 十二、知识文档 YAML frontmatter（Obsidian 兼容）

`04_写作知识库`、`02_原著蒸馏`、`03_作品工程` 下的人工/生成文档，首选在文件头部带
YAML frontmatter（至少 `title`、`tags`、`source`），便于未来在 Obsidian 等双链笔记软件里
索引、反链、检索。

- **仅约定 frontmatter 规范，不引入 Obsidian 依赖、不新建顶层目录、不提交 `.obsidian/` 配置。**
- 正文用普通 Markdown，不依赖 Obsidian 专属语法，保证通用可读。
