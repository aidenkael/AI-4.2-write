# AI-write 项目推进记忆

> 保存跨会话必须记住的项目方向、重大决策和当前阶段。过程日志不放这里。

## 1. 最终目标

AI-write 是作者主导、AI 辅助的中文长篇小说工作台。

作者主要做：`看正文 → 说感觉/要求 → 接受/拒绝/继续修改 → 做重大创作取舍`。

系统主要做：`知识召回 → Context 编译 → Skill/Agent 路由 → 规划/写作/诊断/修改 → 连续性 → 状态回写`。

前期原著蒸馏和后期辅助创作是一条链；后台复杂度应尽量对作者隐藏。

## 2. 长期原则

- Borrow-first；
- 案例只暴露问题，不决定架构；
- 真实任务优先，非必要不升级 Benchmark；
- BKP 与原创 Canon 严格分离；
- **作者控制 ≠ 作者审批**；
- 作者不维护后台字段或手动挑 Skill；
- 正式创作阶段性冻结核心工作流；
- 长期文档只留稳定原则，不持续堆过程细节。

## 4. G4 稳定结论

G4 证明了一个最小创作中枢可以成立：

`Author Intent + Story State + Creation Brief + 少量 BKP → 小 Context / 候选方向 → 作者自然语言反馈 → Decision Record / 合法 State Diff`

长期保留：

- 创作现场可以文件化恢复；
- Context 应小而相关、可重建；
- state/intent revision 变化后旧 Context 必须 STALE；
- 跨书综合按问题自然发生，不强制多书；
- 非阻塞 BKP gap 只记录，不自动扩库；
- `approved_plan ≠ Canon`，作者可改变旧计划；
- 真实作者反馈才可获得 `author_decision` authority；
- `accepted_text` 明确事实可走 mechanical settlement，歧义/推断不能偷渡；G4 只验证该协议边界，未证明生产级 Writer/runtime；
- 当前无 Retrieval / RAG / KG 升级理由。

## 5. 当前下一步边界

下一 Gate 尚未建立。未来应继续 Borrow-first，从真实创作执行需求选择一个小目标，不一次开发整个 Writer/Reader/Controller/UI 系统。

一个自然的后续方向是把已证明的中枢接到“生成/修改正文 → 作者说感觉 → 后台路由专业能力 → accepted text 状态结算”，但在正式立 Gate 前不实施。
