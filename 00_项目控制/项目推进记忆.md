# AI-write 项目推进记忆

> 用途：记录跨会话、跨阶段仍需保留的项目方向、关键决策与当前优先级。
> 本文件不是 Benchmark 过程日志，不替代各专项 STATUS，也不替代全局能力地图。
> 更新原则：只在阶段边界或重大方向变化时更新，避免把临时 Agent 反馈、单次运行细节堆进来。
> 首次建立：2026-08-10

## 1. 项目最终目标

AI-write 的目标不是长期研究 GitHub 项目本身，也不是建立复杂资料管理系统，而是尽快形成一套作者真正能使用的 AI 长篇网络小说创作工作流：

`素材准备 → 原著蒸馏 → 设定/人物 → 大纲 → 场景规划 → 正文生成 → 连续性检查 → 诊断修订`

GitHub 上游是能力与工程经验来源，不是最终产品。最终应逐步收敛为 AI-write 自己的本地 Skill、知识、上下文组织与工作流。

## 2. 当前研究方法的最终取向

### 能力地图继续保留，但不再当成串行 Benchmark 排期表

全局能力地图继续作为全局导航：遇到真实创作问题时，先判断缺的是人物、情绪、对话、Scene Turn、Memory、Reader Sim、中文自然度等哪种能力，再回到对应候选池取用或验证。

后续默认不按 `B02 → B01 → B04 → B05...` 顺序逐项把全部能力做成重型 Benchmark。真实蒸馏与真实创作将负责暴露瓶颈，再针对瓶颈做最小测试。

全局能力地图 v0.2 收口（G0）已完成并由用户确认退出：已有证据、候选项目、实际比较状态、许可证边界和能力空白已整理清楚，`AI-write_全局能力地图_v0.2.md` 成为正式导航文件。

### 默认采用轻量验证

普通候选以后优先使用：

`快速筛选 → 最小真实任务测试 → 作者快速判断 → 吸收 / 保留候选 / 放弃`

只有同时满足以下条件时才升级为严格 Benchmark：

- 机制可能成为长期核心能力；
- 现有证据明显矛盾或容易误判；
- 错误固化的长期代价较高。

作者主要判断真实文本和真实创作价值；代码、机制、证据、许可证与工程归因由 Controller / Agent 处理。

## 3. 上游项目与许可证处理

许可证受限不等于项目失去价值。

- MIT / Apache-2.0：当前可积极复制、修改、适配，保留必要来源记录。
- CC BY-NC-SA：当前私人、非商业研究可以继续使用和测试；保留来源，未来公开/商业化时重新审计。
- AGPL：当前本地私人研究、运行和修改不自动排除；未来分发软件或提供网络服务时重新审计。
- 许可证不明：可以研究架构、思想和公开行为，但未核实前不复制受版权保护的代码/Prompt 进入 AI-write 核心。

因此 Apodictic、InkOS、NovelForge、AI-Novel-Writing-Assistant 等没有因为许可证问题被“淘汰”；它们继续留在能力地图和候选池中，在适合的能力赛道使用。

下一轮地图收口必须为重点项目显式增加 `实际比较状态`，至少区分：正式实测 / 轻量实测 / 仅代码或架构审阅 / 未实测。不得因为某项目出现在候选池、曾被讨论或未参加某个专项，就推断它已经比较、失败或被淘汰。

- D0 strong baseline：自然具备部分能力，部分任务中表现稳健。

不启动 B02-R / Round2B / M1+M2 组合。不创建 AI-write Candidate。不写入正式知识库。后续把 M2/M1 带入真实创作观察，只有真实创作出现矛盾或高价值问题时才重新验证。

## 9. 防跑偏与同步提醒

项目阶段顺序以 `项目阶段门禁.md` 为明确约束。新 Agent 开始任务时必须先说明：当前门禁、本次唯一主目标、禁止范围、本次准备完成的退出条件。

单次聊天中的临时建议不能自动改变项目阶段；若与仓库长期记录或用户最新确认冲突，应停止并重新对齐。

若 GitHub 远端先更新而本地尚未同步：下次 Agent 开始工作时必须先 `git fetch origin`，检查本地工作树和差异；确认不会覆盖用户本地修改后，再以正常 fast-forward / pull 方式同步。不得 reset/restore/clean 本地内容。
