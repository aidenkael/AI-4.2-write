# AI-write 项目推进记忆

> 用途：记录跨会话、跨阶段仍需保留的项目方向、关键决策与当前优先级。  
> 本文件不是 Benchmark 过程日志，不替代各专项 STATUS，也不替代全局能力地图。  
> 更新原则：只在阶段边界或重大方向变化时更新。  
> 首次建立：2026-08-10；最近重大更新：2026-08-11。

## 1. 项目最终目标

AI-write 的目标是建立一套能长期辅助**不同题材、不同风格长篇小说**的 AI 创作工作台，而不是只优化某一本书、某一种网文套路，也不是长期研究 GitHub 项目本身。

作者层尽量简单：

`参考/研究 → 构思 → 规划 → 写 → 审阅 → 修改`

后台负责：

`Book Knowledge + Canon/Memory + Retrieval + Context Compiler + Planning + Writer + Critic/Reader/Editor + Continuity + Controller`

作者负责创作方向、人物取舍、审美判断和重大改变；系统负责资料、记忆、检索、诊断、状态同步与技术路由。

## 2. 长期开发原则

### 2.1 Borrow-first

优先搜索、比较并借鉴成熟开源能力，不因为“必须原创”而重复造轮子。

AI-write 自研重点应收缩到：

- 协议；
- 路由与胶水；
- Book Knowledge Package（BKP）；
- BookProfile 的蒸馏预算逻辑；
- 中文长篇适配；
- 作者控制；
- 必要的状态接口。

Writer、Critic、Reader、Planning、Canon、Memory、Continuity、RAG/KG、Story Bible 等若已有成熟实现，先借/改，再判断真实缺口。

许可证类型不作为当前私人研究阶段的技术淘汰标准，但实际复制/修改仍保留来源、上游 commit/tag、LICENSE 与改动范围；未来公开、商用、服务化或分发时重新审计。

### 2.2 能力地图是长期路由，不是串行 Benchmark 排期

C01–C20 与 GitHub 候选池长期存在。默认路线：

`真实蒸馏/创作问题 → 能力地图定位 → 候选方案 → 最小真实测试 → 吸收/保留/放弃`

普通能力默认轻量验证；只有高价值、证据矛盾、错误固化代价高时才升级严格 Benchmark。

### 2.3 作者不是机器

系统不能要求作者每天手动挑十几个 Skill、维护几十份状态表或严格服从旧大纲。

作者偏离计划时，正确行为是：

`识别影响 → 告知后果 → 作者确认 → 更新大纲/Canon/后续状态`

## 3. 原著蒸馏战略已经升级

### 3.1 当前 BookDistill v0.1.1 的真实定位

BookDistill v0.1.1 已证明 evidence-first 地基有效：

- 可消费 SourcePrepare PASS；
- 逐章读取并保留 FACT / INFERENCE / MECHANISM / BOUNDARY；
- 有来源 snapshot/fingerprint；
- 有章节、book_id、行号等机械校验；
- 能从跨章证据形成作者可读综合层。

但它**不是最终可规模化的蒸馏器**。两本真实作品暴露：

- `model.md + mechanisms.md` 偏向高度总结；
- 容易把大型作品压成十几条整齐“总钥匙”；
- 人物、关系、场景、对白、情绪、叙事、语言、长篇连续性等细粒度知识可能被压掉；
- 单书 Pattern 容易被写成过度确定的“写作规律”；
- 尚不能证明一本书处理完后，未来写作只需检索而无需再次蒸馏。

因此当前版本保留为 **BookDistill vNext 的证据地基**，暂停直接规模化。

### 3.2 已完成的两本真实样本

`book_0038 一九八四`：

- 348 条 evidence；85 条原始 MECHANISM；15 条最终机制；精选 evidence 70；
- 作者认为可理解、有启发，但无法仅凭阅读判断是否真正提升写作；
- G1 已由用户确认退出；未达 M5。

`book_0065 三体`：

- 42/42 章；899 条 evidence（390 FACT / 181 INFERENCE / 244 MECHANISM / 84 BOUNDARY）；
- 244 → 17 条正式机制；精选 evidence 74；assemble errors=0 / warnings=0；
- 与《一九八四》明显不同，说明方法能跨书工作；同时暴露“压缩过强”的核心问题。

## 4. BookProfile 的最终原则

BookProfile **不能先读一小部分就决定哪些维度不蒸馏**。

正确顺序：

`全维度基础蒸馏 → BookProfile → 识别明确强项/潜在强项/普通项/不确定项 → 1～N 次专项深挖 → Profile 反向修正`

BookProfile 负责分配后续 token / 深挖预算，不拥有永久删除某维度的权力。

每个维度至少考虑：

- 当前价值判断；
- 支撑证据量；
- 置信度；
- 反例/不确定性；
- 是否需要专项深挖。

必须允许一本书被判断为“多维度都非常优秀”，此时应增加蒸馏预算，而不是强行只选几个重点。

## 5. 一本书的蒸馏次数不固定

目标不是“最少几次”，而是：

> 一本书处理完成后，大部分对未来创作有价值的知识已经固定进入 BKP；日常正式写作通常只检索，不重新蒸馏整本原著。

默认模式：

`Pass 1 全维度基础蒸馏 + Pass 2～N 专项深挖 + 交叉验证/去重/连接 + BKP 封装`

普通或单项突出作品可以较少次数；多项优秀或全能型作品可以蒸馏 3～5 次甚至更多，只要每一遍解决明确问题。

例外：未来系统新增今天没有定义的重要能力维度时，可以对旧书进行“系统升级式再蒸馏”。

## 6. Book Knowledge Package（BKP）

BKP 是一本参考书最终进入 AI-write 的长期固定知识资产，不只是漂亮总结。

长期需要兼容：

- 作品身份/来源/版本/provenance；
- BookProfile；
- 故事、结构、人物、关系、场景、情绪、对白、信息、节奏、世界观、叙事、语言、长篇连续性、读者体验等通用层；
- 作品特有的可扩展知识；
- 证据、反例、边界、前提、失败模式、置信度；
- 能力/题材/场景功能/关系/情绪/信息任务等检索标签。

最大难点不是 Markdown/JSON 文件格式，而是：

1. 粒度：不能 17 条太粗，也不能 899 条全直接塞给写作模型；
2. 推断边界：不能把单书观察写成普遍真理；
3. 跨书统一但不压平不同题材；
4. 未来能按具体创作任务准确召回；
5. 跨书重复只能增加支持度，不能自动变成 Production Rule。

## 7. 知识等级：防止 AI 自己写规则再固化

正式采用：

`Source Evidence → Observation → Pattern Hypothesis → Cross-book Pattern → Creation-tested Heuristic → Production Rule`

单本作品的 mechanism/pattern 默认只属于作品内观察/假设。

只有经过跨书支持和真实创作验证，才可能进入更高层。Production Rule 应极少出现。

B02 M2“人物特异性反应”目前只是 M3 初步验证的强方向性候选；B09 K1–K4 仍为候选机制。它们都不能被当作普遍写作定律。

## 8. GitHub 能力审查需要随新版架构重做一轮

G0 候选池不是失效，而是当时问题定义较窄。现在目标已经升级为完整工作台，应允许一次**有边界的能力层再搜索/复查**。

重点能力层：

- 原著知识化 / 文学分析；
- Story Bible / Canon；
- 长篇规划；
- Writer；
- Memory；
- Retrieval / RAG / KG；
- Continuity；
- Reader / Critic / Editor；
- Context compilation；
- Controller / author control。

每层只需找到足够成熟、差异清晰的 2～4 个方案，并给出：

`直接借 / 改造后借 / 只借方法 / 不适合 / 仍需自研的真实缺口`

达到覆盖后停止搜索，不无限扩张。

已知重要旧候选继续包括 ani-book、oh-story、creative-writing-skills、Apodictic、NovelClaw、InkOS、NovelForge、AI-Novel-Writing-Assistant、AuthorAgent、novel-creator-skill、autonovel 等；新版复查可加入 Story Bible/KG、一致性分类、层级规划、书籍信息抽取等新方向。

## 9. 工作台“里子”和“面子”分离

当前先做后台“里子”：知识、状态、检索、规划、写作、诊断、修订、Controller。

界面“面子”暂不定死：

- 开发阶段：Agent + Markdown/Git；
- 近期作者使用可考虑 Agent + Obsidian；
- 中期根据真实痛点评估 Obsidian 插件或本地 Web；
- 是否做独立软件最后再决定。

后台必须与界面解耦。Agent 是发动机，界面是驾驶舱，Markdown/结构化数据/数据库/Git 中的作品与知识才是长期资产。

## 11. 当前正式阶段与优先级

当前 Gate 仍为 **G2**，但用户已确认 G2 的战略目标需要重写：两本真实作品已经完成足够的跨书验证，现在不能沿旧路线直接进入 G3。

当前唯一主线：

`有边界 GitHub 能力层复查 → 定义 BKP / BookProfile → 设计 BookDistill vNext → 再决定实现/验证和下一 Gate`

`G2 只再蒸馏 1–2 本 → 直接 G3 正式作品工程`

已不再自动成立。

## 13. 防跑偏与闭环更新

根目录 `AI-write_长期开发手册.md` 是长期架构与路线总纲；`当前工作索引.md`、本文件、`项目阶段门禁.md` 负责当前执行状态。

每次 Gate closeout 或重大架构变化确认后，必须检查并同步更新：

1. `AI-write_长期开发手册.md`（含 AUTO 当前状态/下一步/风险区）；
2. `当前工作索引.md`；
3. `项目推进记忆.md`；
4. `项目阶段门禁.md`；
5. `AGENTS.md`（长期规则发生变化时）；
6. 相关 STATUS / provenance。

然后 commit、报告 SHA；**没有用户明确确认，不自动进入下一 Gate。**

Git 同步继续遵守：未知本地/远端差异先 fetch+compare，不 reset/restore/clean，不自动清理 Local Only/untracked。
