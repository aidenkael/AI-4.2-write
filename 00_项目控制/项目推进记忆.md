# AI-write 项目推进记忆

> 用途：记录跨会话、跨阶段仍需保留的项目方向、关键决策与当前优先级。
> 本文件不是 Benchmark 过程日志，不替代各专项 STATUS，也不替代 `AI-write_全局能力地图_v0.1.md`。
> 更新原则：只在阶段边界或重大方向变化时更新，避免把临时 Agent 反馈、单次运行细节堆进来。
> 首次建立：2026-08-10

## 1. 项目最终目标

AI-write 的目标不是长期研究 GitHub 项目本身，也不是建立复杂资料管理系统，而是尽快形成一套作者真正能使用的 AI 长篇网络小说创作工作流：

`素材准备 → 原著蒸馏 → 设定/人物 → 大纲 → 场景规划 → 正文生成 → 连续性检查 → 诊断修订`

GitHub 上游是能力与工程经验来源，不是最终产品。最终应逐步收敛为 AI-write 自己的本地 Skill、知识、上下文组织与工作流。

## 2. 当前研究方法的最终取向

### 能力地图继续保留，但不再当成串行 Benchmark 排期表

`AI-write_全局能力地图_v0.1.md` 继续作为全局导航：遇到真实创作问题时，先判断缺的是人物、情绪、对话、Scene Turn、Memory、Reader Sim、中文自然度等哪种能力，再回到对应候选池取用或验证。

后续默认不按 `B02 → B01 → B04 → B05...` 顺序逐项把全部能力做成重型 Benchmark。优先让真实蒸馏与真实创作暴露瓶颈，再针对瓶颈做最小测试。

### 默认采用轻量验证

普通候选以后优先使用：

`快速筛选 → 最小真实任务测试 → 作者快速判断 → 吸收 / 保留候选 / 放弃`

只有同时满足以下条件时才升级为严格 Benchmark：

- 机制可能成为长期核心能力；
- 现有证据明显矛盾或容易误判；
- 错误固化的长期代价较高。

作者主要判断真实文本和真实创作价值；代码、机制、证据、许可证与工程归因由 Controller / Agent 处理。

## 3. 上游项目与许可证处理

许可证受限不等于项目失去价值。

- MIT / Apache-2.0：当前可积极复制、修改、适配，保留必要来源记录。
- CC BY-NC-SA：当前私人、非商业研究可以继续使用和测试；保留来源，未来公开/商业化时重新审计。
- AGPL：当前本地私人研究、运行和修改不自动排除；未来分发软件或提供网络服务时重新审计。
- 许可证不明：可以研究架构、思想和公开行为，但未核实前不复制受版权保护的代码/Prompt 进入 AI-write 核心。

因此 Apodictic、InkOS、NovelForge、AI-Novel-Writing-Assistant 等没有因为许可证问题被“淘汰”；它们继续留在能力地图和候选池中，在适合的能力赛道使用。

B02-G Round1（exploratory）与 Round2A（单机制隔离）均已完成。作者盲评封存、Controller 独立评审、5 份外部 AI 独立评审、正式揭盲与最终分析均已完成。B02 本阶段暂停。

最终证据等级：

- M2「人物特异性反应」：M3 初步验证。强正向方向性候选。作者 G1-G3 一致选择 M2，5/5 外部 AI 在 G1/G3 一致选 M2。但仅 2 任务 × 2 重复，G4 执行不佳，不能称为普遍写作规律。
- M1「解释抑制」：M2 协议可测。更适合作为轻量修订检查候选。G4 表现突出但 G1-G3 不稳定。
- D0 strong baseline：自然具备部分能力，部分任务中表现稳健。

不启动 B02-R / Round2B / M1+M2 组合。不创建 AI-write Candidate。不写入正式知识库。后续把 M2/M1 带入真实创作观察，只有真实创作出现矛盾或高价值问题时才重新验证。

### SourcePrepare

已回收到 main，v0.2.1。全库 dry-run 已正确发现 141 部作品、6 类目录，合集与索引逻辑已有测试覆盖。

当前不要立刻全量转换。为了启动真实蒸馏，只需要先选 1 部代表性书做真实转换，拿到可靠 `PASS` 标准输入即可。异常 EPUB、多格式交叉校验和批量转换可以在确实需要时再补。

### BookDistill

main 尚无可用实现。旧分支只有 v0.1.0 接口草案，定义了：

`SourcePrepare PASS → 读取 full.md / chapters → 输出到 02_原著蒸馏/<作品ID>_<作品>/`

下一阶段应把它做成“最小可用 BookDistill v0.1”，而不是先建设完整蒸馏平台。

实现时优先继承 B09/ani-book 已证明有价值的纪律：证据可追溯、fact/inference/hypothesis 分离、覆盖范围、置信度/边界；但输出必须以作者实际可用为标准，避免过重 schema 和报告工程。
