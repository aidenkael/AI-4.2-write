## G3 证明了什么

1. 多个 BKP 可以共同存在；
2. 一个真实创作问题可以跨书召回少量相关知识；
3. 返回知识可追溯到作品、知识条目和必要 Evidence；
4. Scope / Boundary / Counterevidence 不在检索过程中丢失；
5. 单书 Pattern 不会因为跨书检索自动升级成写作规则；
6. 当前最小 KnowledgeRetrieve 足以证明链路成立，不需要为了工程完整度升级大型 RAG/KG。

## G3 没有证明什么

- 没有证明 BKP 已捕获每本优秀作品全部精华；
- 没有证明多书智慧已经自动综合成最佳原创方案；
- 没有证明 Writer 已经因为 BKP 而写出更好的小说；
- 没有证明当前关键词/bigram 检索是最终检索架构；
- 没有产生新的 Production Rule。

这些边界不是“未收尾”，而是后续 Phase E/F 的正式验证对象。

## 已确认的三个系统性缺口

### 1. 原著 Discovery orchestration

**已在 G3 closeout 前完成方法级修正。**

默认：

- 长篇运行 / 读者动力镜头：优先借 oh-story + AI-Novel；
- Reader / Page Craft 镜头：优先借 creative-writing-skills；
- 必要时 Developmental Deep Dive：优先借 Apodictic；
- BookDistill 负责回源核证、去重、组合效果、边界/反例/置信度和 BKP 封装。

### 2. Cross-book synthesis

**留给 Phase E。**

由 Context Compiler / Muse / Planner 根据作者意图、当前 Story State、读者目标和少量 BKP Hit 做情境化综合，不由 Retrieval 自行发明普遍规律。

### 3. Author decision loop

**留给 Phase E。**

AI 提供方案、证据、风险和推演；作者做重大创作决定；系统按确认结果更新计划 / Canon / 后续状态。

## 下一阶段建议入口

下一正式方向：**Phase E｜创作核心后台**。

启动前先做一次很小的 Borrow-first 组合设计，优先确认成熟上游如何承担：

`Story/Project Bible + Canon → Context Compiler → Planner/Outliner → Writer → Reader/Critic/Editor → Continuity → State Writeback → Controller/Author Decision Loop`

其中跨书 Synthesis 作为 Context Compiler / Muse / Planner 的接口问题处理。

不建议下一步：

- 继续打磨 Retrieval；
- 新建大型 RAG/KG；
- 批量蒸馏更多书；
- 重新跑《一九八四》《三体》；
- 再建研究型 Benchmark；
- 直接把正式长篇当开发试验品；
- 从零重造成熟 Writer / Canon / Reader / Editor / Continuity。
