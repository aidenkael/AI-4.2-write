# AI-write 项目阶段门禁

> 当前 Gate、允许动作、退出条件和禁止范围的权威入口。更新时间：2026-08-12。

## 1. 当前 Gate

**G4｜创作上下文与作者决策最小闭环：ACTIVE / G4-C。**

G4-A：完成。  
G4-B：完成。  
G4-C：进行中。  
G4-D/E：未开始。

## 2. G4-C 唯一目标

用真实本地文件与现有 `KnowledgeRetrieve` 证明：

`Author Intent + Story State + Creation Brief + 少量 BKP Hit`

可以被编译成**小而相关、来源清楚、可重建**的 Context Package，并进一步对当前原创问题形成少量情境化综合方向。

本阶段至少覆盖：

1. 偏人物问题；
2. 偏情节 / 信息问题；
3. 偏读者体验问题。

## 3. 当前执行方式

G4-C 由本地 Agent 执行真实文件/脚本验证。

执行任务：`06_工作区/G4C_Agent任务_最小Context与跨书综合.md`。

现有 Retrieval：`05_Skills与自动化/01_Skills/KnowledgeRetrieve/run.py`。

沙盒权威工件：
- `06_工作区/G4B_沙盒_雾港档案室/author_intent.md`
- `06_工作区/G4B_沙盒_雾港档案室/story_state.yaml`
- `06_工作区/G4B_沙盒_雾港档案室/briefs/brief-001.md`

## 4. G4-C 必须证明

- KnowledgeRetrieve 被真实运行，而非手工模拟；
- Context 不全量塞 Author Intent、Story State 或 BKP；
- 每个被选条目都能说明为什么与当前问题相关；
- BKP Hit 保留来源、scope/boundary/confidence 等已有边界；
- 多书经验存在互补/冲突时能显式比较；
- 只有一本真正相关时不强行制造“跨书共识”；
- 没有足够知识时明确报告 gap；
- 至少形成 1～3 个真实有差异的候选方向；
- 所有 Context / Synthesis 都保持派生身份，不写 Canon；
- 三类问题都完成最小验证。

## 5. 当前禁止

- 修改 KnowledgeRetrieve，只为提升命中率或让结果更漂亮；
- 升级 embedding / vector DB / reranker / KG；
- 修改 BookDistill / BKP；
- 批量蒸馏新书；
- 强行让每个 Context 都同时包含《一九八四》和《三体》；
- 把 BKP Pattern、AI 推演、Context 直接写进 Story State；
- 修改沙盒的 Author Intent / Story State，除非发现 G4-B 文件本身有阻塞性错误并先报告；
- 完整 Writer / Reader / Critic / Editor；
- 正式长篇正文；
- UI / 大型数据库 / KG / 多 Agent 平台；
- 自动进入 G4-D。

## 6. 作者控制边界

**作者控制 ≠ 作者审批。**

本阶段只生成派生 Context 和候选方向，不发生正式 Canon 写回，因此不需要作者逐条审批 Retrieval/Context。

若验证过程中发现必须改变沙盒重大创作方向才能继续，应停止并报告，不由 Agent 自行改写权威状态。

## 7. G4-C 完成条件

Agent 完成真实运行后，应提交一份短报告，至少回答：

- 三类问题各自选了哪些 State / BKP，为什么；
- Context 是否足够小；
- 哪些知识互补、哪些冲突、哪些不适用；
- 生成的方向是否真有差异；
- 有无 Retrieval gap；
- 是否出现必须升级 Retrieval 的真实阻塞；
- 是否修改任何权威工件；
- Git commit SHA 与最终 `git status --short`。

完成后只标记“G4-C 技术验证完成候选”，等待作者确认是否进入 G4-D。

## 8. Git 安全

无明确授权禁止：`reset / restore / clean / force push / rebase / merge`。

已知本地历史 dirty/untracked 不得为本任务清理或纳入提交。只 `git add` 本任务明确产物。

## 9. 防跑偏

- 一次只验证当前 G4-C；
- 真实结果不好就记录问题，不为了过 Gate 改 Retrieval；
- 先证明薄组合可用，再考虑工程化；
- 没有用户明确确认，不自动进入 G4-D。
