## 四、G3 最终验收结论

G3 的唯一核心目标是证明：

> 多个 BKP 可以共同存在；当出现真实创作问题时，AI-write 能从中找到少量真正相关、可追溯、有边界的知识，而作者不需要记住具体参考书和 Pattern 名称。

### 已完成

- G3-A：成熟 Retrieval / RAG / Context selection 方案复查；
- G3-B：最小跨书知识入口 / 检索合同；
- G3-C：《一九八四》+《三体》两个正式 BKP 最小检索原型；
- G3-D：真实创作问题验证；
- 成熟作者完整创作认知能力地图审查；
- 原著 Discovery 方法级修正；
- 作者 closeout 验收。

### G3 已证明

1. 两个正式 BKP 可以同时进入统一知识入口；
2. 真实创作问题可以跨书召回相关知识；
3. 返回结果数量受控，不把完整 BKP 塞入模型；
4. 返回知识可以追溯到作品、知识条目及必要 Evidence；
5. Scope / Boundary / Counterevidence / Confidence 可以保留；
6. 单书 Pattern 不会因为跨书检索自动升级成写作规则；
7. 已验证“只与一本书相关 / 两本书都可能相关 / BKP 无可靠答案”三类问题；
8. 未来 Planner / Writer / Critic 可以拿到“小而相关”的知识包；
9. 当前最小 KnowledgeRetrieve 足以证明技术链，不需要在 G3 内升级大型 RAG/KG。

### G3 明确没有证明

关闭 G3 不得被误读为：

- BKP 已完整捕获优秀作品全部精华；
- BookDistill 已是最终批量蒸馏器；
- 多书智慧已经能自动综合成最佳原创方案；
- Writer 已经因为 BKP 知识而写出更好的小说；
- 当前关键词 / bigram 检索是最终检索架构；
- 单书或跨书 Pattern 已经成为 Production Rule。

完整说明：`00_项目控制/G3_收口记录_2026-08-12.md`。

## 五、G3 收口前完成的原著 Discovery 修正

成熟作者完整能力审查确认：当前 BKP / Evidence / Boundary 等知识纪律较稳，真正薄弱的是“怎样先看见原著真正重要的东西”。

因此 `BookDistill/SKILL.md` 已完成方法级修正：

```text
原著
│
├─ 默认镜头 A：长篇运行 / 读者动力
│  └─ 优先借 oh-story + AI-Novel
│
├─ 默认镜头 B：Reader / Page Craft
│  └─ 优先借 creative-writing-skills
│
├─ 必要时 Developmental Deep Dive
│  └─ 优先借 Apodictic
│
└─ BookDistill 总编辑
   └─ 回源核证 → 去重 → 找组合效果 → 补边界/反例/置信度 → BKP
```

关键约束：

- 重要观察镜头必须可以直接读原著；
- BookProfile 是导航/预算工具，不是过滤器；
- 允许跨句、跨场景、跨章节组合证据；
- 允许“重要但暂时无法命名”的 Observation / Inference；
- Discovery 可以宽，最终 BKP 必须克制；
- 不新增几十个固定 taxonomy；
- 不围绕单个案例打补丁；
- 不改变单书最高默认 Work-specific Pattern 的认识论边界。

本次只改方法说明：**没有改 BKP schema，没有要求重跑《一九八四》《三体》，没有启动第三本书。**

## 六、下一阶段已经明确的正式问题

以下不是 G3 尾巴，而是 Phase E 的正式任务：

### 1. Cross-book synthesis

未来由 Context Compiler / Muse / Planner 根据：

`作者意图 + 当前 Canon/人物/关系/章节状态 + 希望读者经历什么 + 少量 BKP Hit`

做情境化综合，输出少量可选创作方向。

禁止把“多本书都这么写”直接当成普遍规律。

### 2. Author decision loop

目标：

`AI 提供方案 / 证据 / 风险 / 推演 → 作者做重大创作取舍 → 系统按确认结果更新计划 / Canon / Story State。`

优先借：

- creative-writing-skills 的 Muse / 专业角色分工；
- Apodictic 的诊断 Firewall；
- InkOS 的 author_intent / 分支推演 / 确认后写回；
- AI-Novel 的成熟生产工程；
- oh-story 的中文长篇推进与读者动力机制。

## 九、禁止“顺手扩展”

每次 Agent / Controller 任务只推进一个明确目标。

发现其他问题时：

- 可以记录；
- 可以提出下一步建议；
- 不得因为“顺手”“以后会用到”“架构更完整”直接扩大任务。

任何跨 Gate 动作、重大目录变化、新 Benchmark、批量处理或新架构建设，都需要用户明确授权。
