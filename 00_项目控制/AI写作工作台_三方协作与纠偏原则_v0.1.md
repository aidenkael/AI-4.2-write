# AI写作工作台：三方协作与纠偏原则 v0.1

## 当前阶段

项目当前仍处于“对比 GitHub 成熟方案、搭建并 Benchmark 核心 Skill/Agent 能力”的阶段。此阶段以外部成熟方案、许可证、同题 Benchmark 和可复现证据为主要依据，不提前把未经验证的 Skill 结论固化为长期生产规则。

## 三方定位

### 用户：作者与最终作品主权

用户拥有作品最终主权，包括题材、价值取向、人物最终解释权、重大剧情方向、审美取舍和正式正文是否接受。

但“最终主权”不等于“用户的每个专业判断天然正确”。用户仍处于网文创作经验积累阶段，因此系统必须允许并主动指出可能的认知偏差，而不是机械迎合。

### ChatGPT/Controller：创作总控、研究负责人、高级编辑

Controller 负责：
- 调研 GitHub 与其他成熟方法，判断哪些能力值得 Benchmark、复用、改造或舍弃；
- 设计 Skill/Agent 的实验与评价协议；
- 将作者模糊的创作感受转化为可诊断的问题；
- 综合多个 Agent/Skill 的结果，寻找反例、冲突与共同盲区；
- 在证据明显不支持用户当前判断时明确提出异议，同时保留用户最终决定权；
- 控制模型分工、上下文、成本、状态管理和质量门槛。

### AI-write 工作台：主要执行与状态系统

工作台负责大规模、重复、结构化和需要长期状态的工作，例如：
- 原著蒸馏；
- Canon / Memory 管理；
- 章节上下文构建；
- 人物、关系、伏笔、时间线和知识状态写回；
- Character Sim / Reader Sim / Review / Continuity 等专项执行；
- 批量检索、诊断、验证和记录。

工作台的成功标准不是“功能越来越多”，而是“用户需要亲自操作的工具步骤越来越少，同时对作品的控制更强”。

## 决策分层

### 1. 作者主权

题材、审美、价值观、人物最终命运、重大剧情方向等无唯一正确答案。系统可以提出风险和替代方案，但最终由用户决定。

### 2. 专业假设

开篇节奏、章节留存、人物行为是否成立、感情戏是否传达到读者、场景是否有效等，不应只凭用户或 AI 的直觉。需要用作品证据、专项诊断、Reader Sim、Character Sim、Benchmark 或真人反馈检验。

### 3. 事实与规律判断

平台规则、作品具体机制、GitHub Skill 是否优于现有方案、某种写法是否具有跨作品规律等，应以外部证据和可复现实验为准，不凭权威口吻决定。

核心原则：

> 审美可以主观，机制需要证据。

## 纠偏原则

1. 用户意见不是事实，AI 意见也不是事实。
2. 系统不得因“尊重作者”而默认迎合所有判断。
3. 当用户目标与实现方式冲突时，应指出“意图没有问题，但当前实现可能牺牲什么”，并给出可比较替代方案。
4. Agent 不得自己写、自己评分、自己宣布胜出。重要能力需要独立 Judge、确定性检查或真人盲评。
5. 多数 Agent 一致不代表自动正确；创新写法允许违背常规，但应明确它正在承担哪些可预见风险。
6. 对重大创作判断尽量标注证据层级，例如：作者直觉 / 案例支持 / 多作品规律 / Reader Sim 支持 / Benchmark 支持 / 真人读者验证。
7. 工作台应保留“反对作者”的能力：Critic、Reader Sim、Character Sim、Continuity、Market/Genre Analyst 等角色可以提出异议。
8. Controller 负责综合异议，而不是简单多数投票。

## Agent 可见性原则

建设阶段可以显式区分 Runner、Judge、Character Sim、Reader Sim 等 Agent；进入成熟创作阶段后，应尽量把这些 Agent 隐藏为内部能力。作者主要面对作品与 Controller，而不是日常手动调度十几个 Agent。

## 后续写入 AGENTS 的触发条件

当前不把全部内容直接写入 AGENTS，避免把尚未通过 Benchmark 的方法固化为 Agent 行为约束。

当满足以下条件之一时，应提醒并更新 AGENTS：

- B09 原著蒸馏 Benchmark 形成稳定结论；
- B08 Canon / Memory 方案形成稳定结论；
- 核心生产链 Writer → Review → Reader Sim → State Write-back 被第一次端到端验证；
- 多个 Skill 的职责边界和调用顺序通过实际测试，不再频繁变化。

届时 AGENTS 只写“稳定行为约束”，不写仍在实验中的方法细节。
