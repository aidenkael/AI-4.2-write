# Author Burden Review｜最小作者体验模拟

> 状态：FROZEN（2026-08-15）。
> 判定：**DEVELOPER_OR_AUTHOR_BURDEN_GAP = YES**（流程操作层面；作者认知层面为 NO，见第 3 节）。

## 1. 理想工作台中作者需要做的事

- 说“我想写这个场景”（一句话 + 少量澄清）；
- 阅读正文；
- 说哪里不对 / 接受 / 要求再改。

共 3 个动作，全部是创作判断，零后台操作。

## 2. 本实验实际发生的操作（由实验者扮演全部角色）

| # | 工件 / 操作 | 性质 | 作者应否接触 |
| --- | --- | --- | --- |
| 1 | 决定使用 Story State rev2 + 显式 simulation gate | 版本与 authority 决策 | 否 |
| 2 | 撰写 `writing_brief.md`（场景范围/欲望/障碍/义务/open space） | 半创作半机械 | 仅“想写什么”部分属于作者，其余应由后台从一句话扩写后请作者确认 |
| 3 | 手工撰写 `creation_brief.json` | 机械（字段搬运） | 否 |
| 4 | 手工 semantic selection（9 条 + 逐条 reason） | 后台智能判断 | 否 |
| 5 | 运行 Python 编译脚本、核对输出 | 机械 | 否 |
| 6 | 手工撰写 `premise_bridge.md` | 实验特有（因无前置正文） | 否（真实流程中前文是 accepted_text，衔接应由后台生成） |
| 7 | 写 W0 | 创作核心 | 作者只读结果 |
| 8 | 五立场诊断并记录 | 后台判断 | 否 |
| 9 | W1 修订与修订记录 | 创作核心 | 作者读结果并给反馈 |
| 10 | postmortem / 归档 | 机械 | 否 |

作者真正需要“创作判断”的只有：场景意图（#2 的一部分）、阅读 W1、接受或反馈。其余 8 项全部可由后台承担。

## 3. 缺口定性

- **作者认知负担：低。** 全部流程中没有任何一步要求作者理解 state id、Context、Skill、Agent、BKP 或 Schema。这说明 E1–E3-A 的合同设计在“对作者隐藏复杂性”上方向正确。
- **开发者操作负担：高且重复。** 每个新场景都会重复 #1–#6、#8、#10；其中 #3/#4/#5 是纯机械搬运，#1 是容易出错的 authority 决策（本实验需要人工判断 rev1/rev2 与 simulation gate）。
- 因此记录 `DEVELOPER_OR_AUTHOR_BURDEN_GAP`：缺口不在“作者被迫操作后台”，而在“后台流程本身尚需开发者手工摇柄”。实验内部人工操作这些工件是合法的；最终产品不能要求任何人（包括作者与日常开发者）逐场重复。

## 4. 负担最重的三个环节（未来薄封装的优先序证据）

1. **Brief 编译**：一句话意图 → 完整 creation brief（含 source_versions 自动对齐、inherited obligations 从 active planning 自动带出）。本次 #2/#3/#4 的大部分工作量在此。
2. **State 版本与 authority 的默认策略**：当前最新合法 State + production authority 应为默认路径，simulation gate 只属于实验。本次 #1 的决策本不该存在。
3. **诊断与修订记录的归档**：五立场诊断 + 修订记录目前是手工 Markdown；若保持轻量模板化（而非建 Review 平台），即可让“后台判断”可追溯而不增加维护负担。

## 5. 对最终工作台的含义

- 作者界面只需要：一句话输入、正文阅读、反馈三件事——本实验证明这三件事之外的所有环节都是派生机械工作。
- 若未来为弥合本缺口而开发，唯一正当形态是**薄流程入口**（复用现有 Intent / State / StoryPlan / Context Compiler 合同），不是新 runtime、新 Schema、新平台；且必须等到第二个场景再次重复同样手工成本后才启动（见 final_report §开发决策）。
